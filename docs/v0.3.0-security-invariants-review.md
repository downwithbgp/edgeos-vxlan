# v0.3.0 — security-invariants review

**Scope:** the six lifecycle questions raised by the maintainer before hardware acceptance. This is a
focused review of the implementation on `feat/native-firewall`, not a replacement for the hardware
runbook.

**Evidence classes used below:**

| Class | Meaning |
|---|---|
| **Source** | Established by reading the implementation (and, where stated, the vendor engine's strings/logic). |
| **Emulated EdgeOS** | Observed by running the official EdgeOS 3.0.1 configuration engine and `ubnt-fw` under qemu in a privileged container, with the platform's iptables replaced by the host's x86_64 legacy iptables (see `v0.3.0-off-device-evidence.md` for the emulation caveats). |
| **Linux netns** | Generic Linux dataplane test; proves the kernel/netfilter semantics, not EdgeOS compatibility. |
| **Hardware required** | Cannot be established off-device; must be measured on the ER-X. |

The review found two real gaps in the first RC, both fixed in the hardening commit:

1. the activation gate only proved that *some* matching jump existed (`iptables -C`), so a duplicate,
   stale, or shadowed dispatch could pass;
2. the apply/verify path did not re-check that the configured ruleset still existed and that its chain
   was non-empty, so an out-of-band ruleset deletion could leave an interface up with a dangling or
   empty target chain.

The current implementation replaces that with an exact, whole-chain verification (see §3).

## 1. Transient fail-open during attachment replacement on an already-up interface

### Normal replacement path (source)

For an attachment-only change the reconciler:

1. captures the live dispatch (`--capture`);
2. calls `--apply`, which invokes one `ubnt-fw update-interface update` for the changed
   direction/family;
3. verifies the new jump immediately (`iptables -C`);
4. runs the strict gate (`--verify-all`) before the interface is touched;
5. applies mutable state and, if the interface is already up, leaves it up.

The interface is **not** recreated for an attachment-only change (mock test 40). A failed replacement
keeps the previous dispatch (still a valid policy) and leaves the interface up; the commit fails and
reports the failure (mock test 42, unit test “failed replacement keeps interface up”).

### The vendor call's internal sequence (source + empirical)

`ubnt-fw` is a stripped vendor binary, so the exact sequence was established empirically: the
installed 3.0.1 binary was run under `qemu-mipsel-static` with a logging `iptables` wrapper. For every
`update-interface` call it issued exactly one mutation:

```text
no existing jump:  iptables -t filter --insert VYATTA_FW_IN_HOOK 1 --in-interface vxlan42 --jump VXLAN_IN
existing jump:     iptables -t filter --replace VYATTA_FW_IN_HOOK 1 --in-interface vxlan42 --jump VXLAN_IN
replacement:       iptables -t filter --replace VYATTA_FW_IN_HOOK 1 --in-interface vxlan42 --jump VXLAN_IN2
removal:           iptables -t filter --delete VYATTA_FW_IN_HOOK 1
```

`iptables` applies the whole filter table in one kernel transaction, so a replacement is atomic: a
packet sees either the old jump or the new one, never an absent jump. There is **no delete-then-insert
gap** inside the vendor call. A ruleset rebuild (`update-rules`) is likewise one
`iptables-restore -n -v` transaction (the restore stream was captured and shows the complete `*filter`
block plus the default-action rule, applied as one commit).

### The architectural guarantee (source + unit)

The package does not rely on that vendor atomicity for the transition that reduces enforcement. When
an apply removes an existing dispatch from an interface that is administratively up, the helper
quiesces the interface first (`ip link set dev down`), performs every change, verifies the complete
desired set, and leaves the interface down. The reconciler activates the interface only after its own
gate passes. A removal followed by a later failure therefore restores the previous firewall snapshot
and only then reactivates the interface. A single replacement or insertion does not quiesce: it is a
single atomic table commit and does not reduce enforcement.

Multi-attachment commits apply one atomic operation per direction/family. Each direction always holds
either its previous or its new policy; no direction becomes unfiltered unless a removal was
requested, and that case is quiesced.

What remains dependent on vendor behaviour: a firewall-*ruleset*-only commit rebuilds the target
chain in the vendor's own commit unit. That transition is a single `iptables-restore` transaction
(source + emulated evidence), but it is not owned by this package and cannot be quiesced from the
interface reconciler. Hardware Phase 4 covers it with a continuous negative probe.

Mitigation and acceptance:

* the helper verifies the exact resulting dispatch after every vendor call;
* the parent gate runs before activation and detects a missing/duplicate/stale/shadowed dispatch;
* hardware Phase 4 runs a high-rate negative probe across a live policy replacement and records any
  successful denied probe. A single success is a failure of the acceptance test.

### Direct restore fallback (source + unit)

When the old ruleset is no longer configured but its chain still exists, the restore path inserts the
restored jump **first** and only then deletes the superseded rule. The interface therefore has a
policy throughout the swap; a failed insert leaves the old rule, and a failed delete is detected as a
duplicate and fails the restore (the caller leaves the interface down). Unit test “direct-chain restore
fallback”.

## 2. Ruleset modification or deletion independently of the VXLAN configuration

### Modification (source + emulated + hardware required)

A `firewall name`/`firewall ipv6-name` change updates the target chain in place
(`ubnt-fw update-rules`); the interface dispatch jump is unchanged, so the interface remains attached
to the same chain. `ubnt-fw` may rebuild individual rules inside the chain; that native transition is
not controlled by this package. The hardware Phase 4 probe must cover a ruleset rule change with a
continuous negative probe.

### Deletion while attached (source + emulated)

The vendor engine refuses to delete a ruleset chain that is still referenced by an interface jump
(inferred from the vendor `ubnt-fw` logic and the documented Vyatta behaviour; **hardware Phase 4**
must confirm the exact EdgeOS response). If the deletion is attempted in the same commit as the
interface attachment removal, the firewall-name subtree and the interface subtree are ordered by the
vendor engine; a refused chain deletion fails the commit and leaves the interface protected.

### Out-of-band deletion (source + unit)

The gate now re-checks, for every configured attachment:

* `exists firewall <family> <name>` in the working configuration;
* the target chain exists in iptables;
* the target chain contains at least one `-A` rule (an empty user chain is not enforcement).

If any check fails, the interface is taken down and the commit fails. This covers a chain deleted or
emptied outside a configuration commit on the next VXLAN lifecycle commit. It is not a daemon; an
out-of-band deletion between commits is not detected until the next lifecycle commit (documented
limitation).

## 3. Effective-state verification: dispatch, ordering, reachability and terminal policy

The gate verifies four distinct properties, from weakest to strongest:

1. **Dispatch presence.** Exactly one exact rule of the form
   `-A <hook> <flag> <interface> -j <target>` exists.
2. **Ordering within the hook.** There is no duplicate exact rule, no stale or malformed
   same-interface rule, and no preceding non-interface rule (global rule) or preceding
   wildcard/negated interface rule that could shadow the dispatch; preceding simple dispatches for
   other interfaces are allowed.
3. **Reachability of the hook from the base chain.** The base chain (`INPUT` for `local`, `FORWARD`
   for `in`/`out`) contains a jump to the hook, and no earlier rule that matches this interface (or
   is unconditional) carries a terminal verdict. A missing or interface-shadowed hook makes the
   per-interface dispatch **inert even though it is present and correctly ordered**.
4. **Terminal behaviour of the target policy.** The target chain exists in the configured firewall
   tree, is non-empty, and its **last** rule carries a terminal verdict (`ACCEPT`, `DROP`, `REJECT`,
   or the vendor's `RETURN` for `default-action accept`). A chain that ends without a verdict falls
   through to the hook and then to the base chain, so the configured default action would not be
   effective.

Failure modes are explicit: `missing`, `duplicate`, `malformed or stale`, `shadowed by a preceding
rule`, `is not reached from <base>`, `shadowed by a preceding rule in <base>`, `chain is empty`,
`chain is missing`, `does not end in a terminal default action`, `ruleset is not configured`.

Evidence:

* **Source:** the exact-dispatch parser, the base-chain reachability parser and the terminal-default
  parser.
* **Unit:** exact dispatch passes; empty chain, shadowed dispatch, stale same-interface rule,
  duplicate dispatch, non-terminal default, unreachable hook and interface-shadowed base chain all
  fail; another interface's base-chain rule first is allowed.
* **Emulated EdgeOS:** the vendor-created chain and hook shape passes the exact check, and the base
  chains contain `-A INPUT -j VYATTA_FW_LOCAL_HOOK`, `-A FORWARD -j VYATTA_FW_IN_HOOK` and
  `-A FORWARD -j VYATTA_FW_OUT_HOOK`. The R2 rollback path restores the old exact jump.
* **Linux netns:** the dispatch survives netdevice recreation and the kernel enforces the jump
  (`test/integration-netns.sh`).
* **Hardware required:** the real `iptables -S` formatting and the real Vyatta hook contents. The
  parser deliberately fails closed if EdgeOS places a shadowing rule in a base chain; the runbook
  records the observed shape.

**Trust boundaries — what the gate does not prove:**

* It does not interpret the operator's rule semantics inside the target chain. The vendor engine
  builds those rules; the package verifies existence, non-emptiness and a terminal default only.
* Base-chain reachability is bounded. A preceding unconditional jump to a stock EdgeOS feature chain
  is allowed and not analysed recursively, and a preceding rule with source/destination matches is
  not treated as a shadow unless it matches this interface (or is unconditional) and is terminal.
* It is a snapshot check at commit time, not a continuous monitor. Out-of-band drift is caught on
  the next lifecycle commit.

### Configuration API errors and administrative state

* The vendor API exits 1 both for "node absent" and for an internal failure; a failure writes a
  diagnostic to stderr while a negative lookup is silent. The reconciler and the helper treat a
  diagnostic as a fatal error, so a broken configuration read can never be read as "no attachment
  configured" (which would remove enforcement) or as "`disable` absent" (which would bring a
  disabled interface up).
* Administrative state is tri-state (`up`, `down`, `absent`, `unknown`). An unknown read is treated
  as "may be up": a down is attempted and verified, and the message reports exactly what was
  confirmed. A down is never claimed when the down command or its confirmation failed.

## 4. Failure and rollback when the previous firewall state cannot be restored

* `--restore` validates the captured snapshot before touching anything; an empty or truncated
  snapshot is refused (unit tests).
* For each entry the restore checks that the target chain exists and is non-empty, restores or inserts
  the jump, and verifies the exact dispatch.
* If the old ruleset is gone but its chain exists, the direct fallback above is used; if the chain is
  gone, the restore fails.
* On any restore failure the caller (`rollback_live_snapshot` or the mutable-only failure path) leaves
  the interface administratively down and reports the failure. It never brings up an interface with an
  unknown policy.

Evidence: source, unit tests, emulated R2 rollback (injected address failure restored the old
`VXLAN_IN` jump and left the interface up), Linux netns recreation. **Hardware Phase 5** must exercise a
failed restore (for example delete the old ruleset and its chain in the same commit) and observe the
interface down plus the explicit error.

## 5. Cold-boot ordering and enforcement before interface activation

* Template priorities: firewall root 199, ruleset tags 210, interfaces root default 200, vxlan node
  459. Firewall chains should exist before the interface subtree (*inferred* from the vendor engine
  priorities; not yet observed on hardware boot).
* The reconciler applies and verifies the desired attachments **before** `create_vxlan` and before
  `ip link set up`, and gates again immediately before up.
* The `disable` leaf no longer has a `delete:` action. Removing `disable` is handled by the parent
  reconciler after the gate, so no child action can bring the interface up before the gate.
* Emulated EdgeOS first commit created the interface only after the four expected jumps were
  installed.
* **Hardware Phase 7** is the only evidence that can establish the absence of a boot-time fail-open
  window: a continuous negative probe from an external host, starting before boot, must never succeed.
  The project does not claim a zero-exposure interval until that run is reviewed.

## 6. Upgrade behavior for existing operational VXLAN interfaces

* Existing v0.2.2 configurations have no `firewall` leaves; `firewall_configured` is false, so the new
  gate and `--apply` are no-ops. Behavior is unchanged (retained mock scenarios 1–36).
* The package upgrade replaces files only; it does not re-commit configuration, recreate interfaces,
  or change the firewall. The new helper and templates are installed; the existing interface keeps
  its current live state.
* The first VXLAN lifecycle commit after upgrade now performs `--capture`. If the iptables hook chains
  are unreadable, the commit fails closed rather than proceeding without a snapshot. This is a
  deliberate behavior change on a broken platform, not a normal-upgrade path.
* **Hardware Phase 2/8** must confirm an upgrade with a live VXLAN interface (no recreation, no
  firewall change) and the removal safeguards.

## 8. Residual architectural concerns

1. **Vendor replacement sequence** — resolved by instrumentation: the installed 3.0.1 binary issues
   one atomic `--replace` (existing jump) or `--insert` (new jump); there is no delete-then-insert.
   The package does not depend on that atomicity for the one enforcement-reducing transition (a
   removal), which it quiesces. Hardware Phase 4 confirms with a high-rate probe.
2. **Ruleset-change window** — native `ubnt-fw update-rules` rebuilds the chain in a single
   `iptables-restore` transaction (source + emulated evidence). It is not owned by this package, so
   it cannot be quiesced from the interface reconciler; hardware Phase 4 probes it.
3. **Firewall hook and base-chain contents** — the gate verifies the exact dispatch, the hook's
   reachability from `INPUT`/`FORWARD`, and a terminal default action. A stock rule that shadows a
   hook fails the gate closed; the hardware runbook records the observed shape and may need a
   narrowly justified allowance.
4. **No continuous monitor** — out-of-band drift is repaired on the next VXLAN lifecycle commit, not
   immediately.
5. **Bridge enforcement** — routed only; bridged attachments remain rejected.
6. **Package install ordering** — the exact `vyatta-cfg-firewall` pin is intentional for the supported
   firmware; a different firmware version is unsupported and the package will refuse to configure.

## 9. Tests that require an independent external host

The OCI test host is currently unavailable. The following cannot be completed locally and are
deferred:

* unsolicited inbound IPv6 (and inner IPv4) probes from an independent Internet host, including the
  Route64 transfer address and a routed-/56 address;
* positive application connectivity (TCP/TLS/HTTP2) from an external host through the tunnel;
* external negative probes during cold boot, policy replacement, and recreation (the continuous
  fail-open detector). A local host on the underlay/overlay can cover the local equivalents, but not
  the Internet-facing path;
* third-party VTEP interoperability from a different network path.

The hardware runbook marks these **DEFERRED — external host required** and does not treat local
substitutes as equivalent.
