# EdgeOS 3.0.1 — scripted-commit firewall limitation (hardware-proven)

**Status:** established on the ER-X (EdgeRouter X, EdgeOS 3.0.1 build 5862409, Linux
`4.14.54-UBNT`) on 2026-11-26 (UTC). This record takes precedence over off-device assumptions
about how firewall rulesets are applied during a commit.

## The finding

The EdgeOS firewall commit hook misapplies `firewall name` / `ipv6-name` changes when the
configuration session is a **scripted** (script-template) session. It classifies a newly added or
changed ruleset as `static` with an empty rule view, logs
`Unexpected static status [name][<ruleset>]`, and generates an iptables delta of the form

```
*filter
-F <ruleset>
-A <ruleset> ... "<ruleset>-10000 default-action <action>"
```

That delta has two outcomes:

* chain does not exist → `-F` fails (`iptables-restore: line 2 failed`), the commit fails;
* chain exists → the commit **succeeds**, but only the default-action rule remains; the configured
  rules are silently removed.

The same commit content applied from the **interactive CLI** applies the ruleset correctly. A
manual `vyatta-firewall.pl --update-rules name <ruleset>` executed inside a scripted session also
applies correctly, and a TTY makes no difference — the defect is in the commit engine's scripted
path, not in the firewall engine or the session's configuration view.

## Evidence (hardware, isolated test rulesets)

| Test | Session | Result |
|---|---|---|
| Create `VXLAN903_IN_B` (icmp, tcp/8080, established, drop) | interactive CLI | PASS — chain and all rules present; dataplane counters moved |
| Create `VXLAN903_IN_B`, `ZZT2`, `ZZT3` | script-template commit | FAIL — `Unexpected static status`, `-F` on a missing chain, `iptables-restore: line 2 failed`, commit failed |
| Create `ZZT4`, with the chain pre-materialised by the vendor engine before `commit` | script-template commit | commit returned 0, but the chain was flushed to the default-action rule only (rules 10/20 removed) — **silent degradation** |
| Delete a ruleset whose chain was absent | interactive CLI | FAIL — same `-F` on a missing chain; succeeds once the chain is re-materialised first |
| Scripted session with a TTY (`ssh -tt`) | script-template commit | FAIL — same `Unexpected static status` |

`/tmp/fw_commit_fail` retains the failing delta; the engine's own apply run
(`vyatta-firewall.pl --update-rules`) is correct when invoked by hand.

## Scope

Reproduced with pure `firewall name` commits: no VXLAN configuration and no helper involvement.
It therefore affects every interface type and both address families; it is not specific to this
package. Chain-name content and length are irrelevant (several distinct names reproduced).

## Impact on this package

* **Create and attach a ruleset in one scripted commit:** fails closed. The interface hook runs
  before the ruleset is materialised and refuses to attach an unconfigured ruleset
  (`ERROR: firewall ruleset '<name>' is not configured under firewall name`); the previous
  dispatch stays in place and the interface is not left operational without its configured policy.
* **Attach an already-applied ruleset in a scripted commit:** works (subject to the interface
  hook's existing verification).
* **Edit a ruleset in a scripted commit:** the vendor apply can leave an attached chain degraded to
  its default action. The interface hook is not invoked for a ruleset-only change, so this package
  cannot observe that transition. It is a platform-level exposure that equally affects native
  interfaces with native attachments.
* **Interactive commits** preserve the ordinary EdgeOS semantics, including create-and-attach in a
  single commit.

## Required operational rule

Treat firewall ruleset changes as interactive-only on this platform. Automation should not modify
`firewall name` / `ipv6-name` nodes from a scripted configuration session. When a ruleset must be
created by automation, commit it from an interactive session first and attach it in a later commit.

## Rejected workarounds

Pre-materialising a chain from a helper is unsafe: the vendor apply flushes it to the default action
and reports success (proven with `ZZT4`). Arbitrary sleeps do not address a wrong status/delta. A
second firewall engine, a weakened gate or treating a missing chain as success are out of scope for
this project.

## Consequences for the evidence record

The off-device suite validates helper behaviour and the emulated engine's ruleset application, but
it does not exercise the real commit engine's scripted-session path. Any earlier statement that a
scripted commit applies a new ruleset must be read with this limitation. Regression coverage for
the attachment scenarios (create+attach, replacement, shared-ruleset modification, multiple
attachment changes, failure and recovery) should be run in both session types, with the scripted
session expected to fail closed on ruleset creation where the platform does so.

## Follow-up

* If a later firmware fixes the scripted-session apply, re-run the two-session matrix and retire
  this record's operational rule.
* Keep the hardware session record's lifecycle conclusions separate: attachment removal, admin
  state, recreation and commit-confirm rollback remain to be completed (hq_06).
