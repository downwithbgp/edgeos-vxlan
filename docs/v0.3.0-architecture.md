# ADR — v0.3.0 native firewall integration for VXLAN interfaces

**Decision:** implement native EdgeOS interface firewall attachment for `interfaces vxlan` by adding a
priority-less `firewall` configuration subtree that reuses the stock `ubnt-fw` engine, plus a small
lifecycle helper that makes attachment installation, verification, snapshot and rollback part of the
interface reconciliation. Do not patch `ubnt-fw`, do not build a parallel firewall manager, and do not
enable bridge netfilter.

## Context

v0.2.2 provides routed and bridged VXLAN interfaces, dual-family underlay, property reconciliation,
recreation with live-state rollback, deterministic MACs, and native bridge membership. The v0.3.0
request adds native firewall attachment on the VXLAN interface itself.

The platform investigation (`v0.3.0-platform-investigation.md`) established:

* EdgeOS 3.0.1 uses per-interface-type firewall templates that call
  `/usr/sbin/ubnt-fw update-interface`.
* `ubnt-fw` installs a name-based jump in a Vyatta hook chain and resolves rulesets from the
  configuration; it has no interface-type table and no dependency on `Vyatta::Interface`.
* The commit engine groups changes into priority subtrees and is **not** atomic. A failed commit can
  leave some subtrees applied and others not.
* Interface children without their own priority execute before the interface's `end:` action and share
  its commit result. Children with their own priority (the existing `mtu`, `address`, `bridge-group`)
  are independent subtrees.
* The vendor `ip -d` human output is defective on this MIPS build; `ip -j -d` is correct and is what
  the reconciler already uses.

## Decision

### 1. Add the firewall templates under `interfaces vxlan`

For each direction (`in`, `out`, `local`) and each address family (`name`, `ipv6-name`) add a leaf
under:

```text
templates/interfaces/vxlan/node.tag/firewall/<direction>/<family>/node.def
```

The leaves follow the vendor shape for completion and validation: an `allowed` list from
`cli-shell-api listActiveNodes firewall <family>`, a safe-name pattern, and a commit-time validation
call to the project helper. They deliberately have **no `update:` or `delete:` action**. The
reconciler's `end:` action applies the whole desired attachment set while it still owns the
pre-change live state.

**No `priority` is declared anywhere in the firewall subtree.** This is deliberate: the subtree must
stay inside the vxlan interface's priority-459 subtree so that the reconciler's `end:` action runs for
a firewall-only change and so a failure in either part cannot be independently marked committed. This
was verified with the emulated EdgeOS config engine: a child-only change (description, then the
firewall leaves) runs the `[ interfaces vxlan <name> ]` subtree.

The configuration API has an important subtlety: during a subtree's `end:` action,
`existsEffective` reports the nodes in that still-executing subtree as absent. The working-config
`exists` call does see them. The reconciler and helper therefore use `exists` for the desired
attachment set; the distinction is pinned by a template test so a future "cleanup" cannot silently
break the attachment application.

### 2. Reuse `ubnt-fw`; do not patch it

`ubnt-fw` already implements the native semantics we need: ruleset validation, zone/switch-port
checks, hook-chain dispatch, per-family iptables selection, and a single-command replacement/insertion of
an interface jump in the vendor implementation. The exact EdgeOS command sequence (and therefore any
internal replacement window) still requires hardware observation. It accepts `vxlanN` names without a type table. A vendor patch would add maintenance and
provenance cost without a demonstrated need.

### 3. Add `vyatta-vxlan-firewall` as a thin lifecycle helper

The helper is the only new moving part. It provides:

| Operation | Purpose |
|---|---|
| `--validate <if> <dir> <family> <name>` | Commit-time validation: interface shape, direction/family, safe ruleset name, ruleset exists in the working configuration, interface is not a bridge member. |
| `--capture <if>` | Read the effective `in`/`out`/`local` dispatch for both families from the filter table. Returns six canonical lines (`-` for none). Exits **3** when the live dispatch is ambiguous and **4** when the filter table cannot be read, so the reconciler can distinguish an untrustworthy firewall state from a generic failure. |
| `--apply <if>` | Take the pre-change state on stdin, plan the desired set from the working configuration, and apply the differences through `ubnt-fw update-interface`. When a removal of an existing dispatch is required on an up interface, the helper quiesces it first (verified `ip link set down`), applies the whole set, verifies it, and leaves the interface **down** for the caller to activate after its own gate. A single replacement/insert is one atomic vendor `iptables --replace/--insert` and is not quiesced. On failure it restores the pre-change state; a failed new attachment leaves the interface down, a failed replacement/removal restores and reactivates. |
| `--restore <if>` | Restore a captured state during rollback. Verifies the exact dispatch, hook reachability and a terminal default for every restored target. If the old ruleset is no longer configured but its chain still exists, reinserts the jump directly as a bounded recovery; otherwise fails explicitly. Never activates the interface. |
| `--verify-all <if>` | The reconciler's fail-closed gate: exactly one exact dispatch, no stale/duplicate/shadowed rule, the hook reachable from `INPUT`/`FORWARD`, and a non-empty target chain ending in a terminal default. |
| `--remove-all <if>` | Remove all dispatches for the interface after a successful interface deletion. |
| `--status <if>` | Diagnostics inside a configuration session: configured vs effective attachment. |

The helper does not create firewall policy, does not touch other interfaces, and does not flush global
tables. It uses the vendor hook chains and only the rules that match the target interface.

### 4. Capture, apply, quiesce on removal, verify, activate

The reconciler's sequence is:

1. capture the mutable live interface state (identity, MAC, MTU, alias, bridge, admin state,
   addresses);
2. capture the live firewall dispatch separately. An untrustworthy firewall state is a fail-closed
   condition **only when an attachment is configured**: the interface is taken down and the commit
   fails. An intentionally unfiltered interface is left unchanged. A failure to capture unrelated
   mutable state aborts the commit without touching the interface;
3. apply the desired firewall attachment set. A removal, or any change set that needs more than
   one sequential vendor dispatch operation, is quiesced: the interface is taken down first and the
   caller activates it only after its gate passes. A single replacement or insertion is one atomic
   vendor operation and is applied without quiescing;
4. verify every desired attachment is effective (exact dispatch, hook reachability, terminal
   default);
5. delete/recreate the netdevice if the identity changed;
6. apply mutable state and run the gate immediately before bringing the interface up. A gate failure
   is fail-closed (interface down); a mutable-step failure restores the pre-commit dispatch and
   reactivates only when the pre-commit state was up.

Because the firewall change is applied before any interface mutation, a new interface cannot be
created without its dispatch, and a recreation cannot lose its dispatch. The gate covers:

* a firewall action that failed but the engine continued to the parent `end:`;
* a boot/order problem that leaves a dispatch uninstalled;
* an attachment configured on an interface whose dataplane lost the jump;
* an attachment whose hook is not reachable from the base chain (shadowed);
* a target chain that is empty or has no terminal default action;
* a new attachment on an interface that is already up.

If a **new** attachment cannot be established on an already-up interface, the helper restores the
pre-change state and takes the interface administratively down. The commit fails with an explicit
message. A failed **replacement** keeps the previous dispatch (still a valid policy) and leaves the
interface up; the commit fails and reports the replacement failure.

A configuration-API diagnostic after a mutation aborts the process directly (`api_exists` cannot
read a broken configuration as "absent"). Both scripts therefore install an `EXIT` trap while a
mutation is in flight. The documented safe state is:

* **helper**: the captured pre-change dispatch is restored. A request that added an attachment
  leaves the interface administratively down (contained failure); a quiesced multi-attachment change
  is resumed only after the restore succeeds. If the restore fails, the interface is left down.
* **reconciler, in place**: the pre-commit firewall snapshot and the pre-commit administrative state
  are restored.
* **reconciler, recreation**: the normal rollback path runs (previous identity, addresses, bridge,
  firewall and administrative state), or a partially created interface is deleted when there was no
  previous interface. If rollback fails, the interface is left down.

In every branch the original exit status is preserved, and an unexpected post-mutation exit is
reported explicitly on stderr.

### 5. Snapshot and rollback of firewall attachments

The reconciler captures the live dispatch **before** applying the desired set, so the snapshot is the
true pre-commit state, not an after-the-fact reconstruction. On a failed recreation the interface is
torn down and restored from the snapshot. Firewall restoration happens after the netdevice, addresses
and bridge state are restored, and **before** the interface is brought back up.

If restoration cannot be completed (for example the old ruleset was deleted in the same commit), the
interface is left administratively down and the commit fails with an explicit message. This is the
required contained-failure behaviour: a down interface, not an operational unfiltered one. The
emulated-engine failure-injection run exercised this path: a VNI change plus a new attachment, with an
injected address failure, rolled the interface back to the old identity and the old jump.

### 6. Deletion ordering

The firewall leaves have no delete action. On an interface deletion, the reconciler deletes the
netdevice first and only then calls `--remove-all`. This ordering means:

* if interface deletion fails, the dispatch is untouched and the still-live interface remains
  protected;
* if interface deletion succeeds, the dispatch is removed afterwards, so there is no unprotected
  dataplane at any point.

When only an attachment is deleted, the reconciler sees the desired set shrink, removes exactly that
dispatch, and leaves the interface up.

### 7. Reject bridged firewall attachments

`--validate` rejects any firewall attachment when `bridge-group bridge` is present in the working configuration, and
`vyatta-vxlan-bridge --validate` rejects adding bridge membership when firewall attachments exist.
A port attachment cannot enforce L2-forwarded bridge traffic; permitting it would be a false security
claim. Enabling `br_netfilter` globally is explicitly not done.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Manual iptables rules / startup hook | Exactly the out-of-band mechanism the release exists to remove; not native, not discoverable, not lifecycle-managed. |
| Parallel firewall manager in this package | Duplicates `ubnt-fw`'s ruleset parser, chain builder, zones, NAT interaction and platform quirks; high maintenance and regression surface. |
| Patch `ubnt-fw` to add a VXLAN interface type | No demonstrated need: the binary has no type table and accepts the name. A patch would need a new binary, provenance and per-firmware validation. |
| Global `br_netfilter` | Changes the handling of all bridged traffic on the router, affects unrelated interfaces, and still does not make a port attachment the natural enforcement point. |
| Automatic per-interface rulesets | The operator must own policy; the package must not invent permissive or restrictive rules. |
| Pure `ubnt-fw` leaves with no helper | No commit-time validation, no verification that the jump is effective, no snapshot/rollback of attachments, no fail-closed gate. The vendor leaves assume the engine's best-effort ordering; this release's security requirements are stronger. |
| Reordering the vxlan reconciler before the children | The engine's `end:` semantics put the parent after its children; changing that would require vendor changes and would still not solve failed-child continuation. |

## Guarantees and limits

**Guaranteed by the implementation (subject to the hardware acceptance procedure):**

* A VXLAN interface with configured attachments is not brought up if any attachment is not effective.
* An attachment installation or verification failure fails the commit and is reported.
* Rollback restores the previous interface state and, when it can be reconstructed, the previous
  firewall dispatch; otherwise the interface remains down.
* Interface deletion removes the dispatch only after the netdevice is gone.
* Existing unfiltered VXLAN configurations behave exactly as before.
* Firewall policy on unrelated interfaces, rulesets, NAT, routing, conntrack and offload is not
  modified.

**Not guaranteed:**

* A strict zero-exposure interval for every commit-confirm/rollback sequence on a non-atomic engine.
* A zero-gap replacement *inside* `ubnt-fw update-interface`. The helper replaces the dispatch with one
  vendor call and verifies immediately afterwards, but a gap internal to the vendor call cannot be
  closed from userspace; the hardware acceptance procedure measures it with a high-rate probe.
  The gate prevents an *operational* interface without its required attachment, but the engine can
  still leave configuration drift after a failed commit; the operator must not `save` after a failed
  commit (existing project rule).
* Continuous out-of-band monitoring. If someone removes the iptables jump outside a configuration
  commit, the next vxlan lifecycle commit detects and repairs it; there is no daemon.
* Bridged L2 enforcement.
* Authenticated VXLAN; `remote-ip` is not an ingress allowlist.
* Outbound `out` semantics beyond the native EdgeOS meaning (forwarded packets leaving the interface).

## Packaging and provenance

* All new code is userspace and packaged in `edgeos-vxlan`; no kernel module rebuild.
* The existing `Vyatta::Interface` diversion, its hash check, and the kernel module provenance remain
  unchanged.
* New dependencies: the stock `vyatta-cfg-firewall` package (provides the ruleset templates) and
  `iptables` (the native tool). `ubnt-fw` is already part of `vyatta-cfg`, a dependency of
  `vyatta-cfg-system`.
* The package removal guard is extended: removal is refused while saved VXLAN configuration exists or
  while live VXLAN interfaces exist.
