# v0.3.0 — off-device evidence

**Status:** off-device evidence collected. **No hardware acceptance has been executed.** This file
records what was run, what passed, and what the emulation cannot prove.

## 1. Artifact

The configuration-engine run used the official EdgeOS 3.0.1 ER-X image:

```text
File:    ER-e50.v3.0.1.5862409.tar
SHA-256: e3d3fe0697bc01d8d9347f3df2b38ce093c2db69f6fa8ea65170270d59a8fb3d
Version: v3.0.1.5862409.250924.1407
Rootfs:  SquashFS 4.0, xz, 71,742,201 bytes
```

The archive was extracted to a disposable rootfs. The repository's scripts and templates were copied
onto it, and the vendor configuration engine was executed under `qemu-mipsel-static` in a privileged
Linux container. `binfmt_misc` was registered for the MIPS ELF so the vendor shell and Perl scripts
could execute.

### Emulation caveats

* The firmware's MIPS `iptables` cannot initialize the x86_64 kernel's netfilter tables because the
  nftables/iptables kernel ABI structures differ by architecture. The emulation replaces
  `/sbin/iptables`, `ip6tables` and their `-save`/`-restore` forms with wrappers around the host's
  x86_64 `iptables-legacy` binaries, with the host's x86_64 libraries and `xtables` extensions. This
  tests the vendor configuration engine and `ubnt-fw`'s command/parse path, not the MIPS iptables
  binary's own netlink ABI.
* `modprobe` is a no-op in the emulation (the host's VXLAN and IPv6 tunnel modules are already
  loaded); the real module loading path was validated in v0.2.2 hardware testing and is unchanged.
* A second commit in a pre-existing config session exposed a limitation: the emulated engine reports
  existing firewall rulesets as `static` and `ubnt-fw`'s `chain_configured` then reports them as not
  configured. The same `ubnt-fw` code is used by the vendor's own interface templates, so this is an
  emulation/session-setup limitation, not a v0.3.0 design dependency. Attachment-only tests were
  therefore run either on a fresh engine state or with the ruleset also changed in the same commit.
  The real static-ruleset case is explicitly part of the hardware procedure.

## 2. Configuration-engine results

### 2.1 First commit with all six attachment leaves

Config: `firewall name VXLAN_IN`, `firewall ipv6-name VXLAN6_IN`, and a routed `vxlan42` with
`in { name VXLAN_IN; ipv6-name VXLAN6_IN }`, `out { name VXLAN_IN }`, `local { ipv6-name VXLAN6_IN }`.

Result: commit succeeded; `vxlan42` was created UP with MTU 1450. The filter table contained:

```text
-N VXLAN_IN
-N VXLAN6_IN
-A VYATTA_FW_IN_HOOK -i vxlan42 -j VXLAN_IN
-A VYATTA_FW_OUT_HOOK -o vxlan42 -j VXLAN_IN
-A VYATTA_FW_IN_HOOK -i vxlan42 -j VXLAN6_IN
-A VYATTA_FW_LOCAL_HOOK -i vxlan42 -j VXLAN6_IN
```

This confirms the template paths, the interface-name variable, the IPv4/IPv6 family split, and all
three native hook chains.

### 2.2 Failed attachment on a fresh interface

`ubnt-fw update-interface update` was forced to exit 1. Config: new `vxlan42` with an `in` attachment.

Result: commit failed; `vxlan42` was **not created**; no interface jump was installed. Only the
ruleset chain existed. Error:

```text
ERROR: native firewall engine failed to install name attachment 'VXLAN_IN' on vxlan42 (in)
ERROR: Failed to apply firewall attachments for vxlan42.
```

### 2.3 Failed new attachment on an already-up interface

Commit A created `vxlan42` UP with no attachment. Commit B added `in name VXLAN_IN` (the ruleset was
changed in the same commit) and forced `ubnt-fw update-interface update` to fail.

Result: commit B failed; the interface flags changed from `0x1003` (UP) to `0x1002` (DOWN); no
interface jump was installed. Error:

```text
ERROR: requested firewall attachment could not be established; vxlan42 left administratively down.
```

This is the required fail-closed behaviour for an explicitly requested attachment.

### 2.4 Attachment add and remove on an existing interface

Commit A: `vxlan42` UP, no attachment. Commit B: add `in name VXLAN_IN` with a changed ruleset. Commit
C: remove the attachment.

Result: B installed `-A VYATTA_FW_IN_HOOK -i vxlan42 -j VXLAN_IN` and left the interface UP; C removed
the jump and left the interface UP. No commit log failure.

### 2.5 Recreation failure restores the previous dispatch

Commit R1: `vxlan42` VNI 42, `in name VXLAN_IN`, UP (ifindex 3), jump to `VXLAN_IN`. Commit R2:
VNI 43, `in name VXLAN_IN2`, address `198.51.100.1/30`; the `vyatta-address add` step was forced to
fail. The reconciler applied `VXLAN_IN2`, recreated the netdevice (ifindex 5), failed at the address
step, and rolled back.

Result: rollback completed; the interface was UP with the old identity; the filter table contained the
**old** jump `-A VYATTA_FW_IN_HOOK -i vxlan42 -j VXLAN_IN`, not `VXLAN_IN2`. The old ruleset was
static, so the helper's direct-chain fallback reinserted the old jump. The commit failed.

### 2.6 Deletion ordering

`DELETE` removed the netdevice first and then called `ubnt-fw update-interface delete` for the
interface; the jump was gone afterwards. A failed `ip link del` left the interface UP and the jump in
place.

### 2.7 Template/API observations

* `exists` sees nodes added by the current commit; `existsEffective` reports the currently executing
  subtree as absent. The implementation uses `exists` and a template test pins it.
* A child-only change (description, then firewall leaves) runs the vxlan `end:` action, which is why
  the attachment lifecycle is owned by the reconciler rather than by separate leaf actions.
* The static-ruleset emulation limitation in §1 is recorded so it is not mistaken for a production
  behaviour.

## 3. Linux network-namespace dataplane test

`test/integration-netns.sh` was run in a privileged Ubuntu 22.04 container with `iproute2`, `iptables`,
`iputils-ping`, `python3`, and the host VXLAN modules. Result: **28 checks, 0 failures**.

Coverage:

* IPv4 overlay over an IPv4 underlay, both directions;
* IPv6 overlay over an IPv6 underlay, both directions;
* forwarded IPv4 and IPv6 ingress/egress;
* `local` ingress to the router;
* native `out` semantics (locally originated traffic is not matched by `FORWARD -o vxlan42`);
* outer underlay transport remains unaffected by overlay policy;
* multiple VXLAN interfaces are independent;
* established/related forwarded TCP passes; unsolicited inbound forwarded TCP is dropped;
* IPv6 NDP resolves under an IPv6 `local` policy while unsolicited echo is dropped;
* the `-i vxlan42` dispatch survives netdevice delete/recreate and traffic resumes.

This is generic Linux evidence. It does not prove EdgeOS configuration-engine compatibility; the
emulated-engine run above covers that layer separately, and neither replaces hardware acceptance.
