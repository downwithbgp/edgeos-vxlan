# Issue #3 — IPv6 VXLAN Underlay: Risks and Open Questions

**Baseline:** `dc99bce4a1bcfc5d57daed7fc167e98df4441e81` (v0.2.1)
**Likelihood** is stated only where technical evidence supports a judgement; otherwise `n/a`. Severities refer to this feature and the supported platform.

## 1. Prioritized risk register

| ID | Risk | Severity | Likelihood | Detection | Mitigation / treatment | Residual |
|---|---|---|---|---|---|---|
| R1 | **IPv4 regression** while introducing dual-family handling (validation, comparison, MTU, rollback) | High | Low–Medium without tests | Unit suites (`U-V4-*`, `U-ID-1/2`, `U-MTU-1`) + acceptance matrix rows 1–2, 22 | Changes are additive at family-sensitive points; IPv4 canonical form round-trips identically; explicit regression tests; matrix row 22 (upgrade with an existing v4 tunnel) | Low after tests |
| R2 | **iproute2 JSON incompatibility** — target output differs from the expected `local6`/`remote6` shape | High (could recreate/rollback incorrectly) | Low — binary contains the exact key strings and upstream print code matches | Phase 1 hardware capture; parser fixtures; fail-closed parsing | Parser fails closed on unexpected/partial structure (nothing deleted); fixtures updated from the real capture before release | Low–Medium until Phase 1 capture exists |
| R3 | **Unsafe interface recreation** caused by false identity mismatches (e.g. partially parsed live state) | High | Medium if parsing were left as-is; Low with the fix | `U-PARSE-*`, `U-IDEM-*`, `U-FAILCLOSE-*`; mocked recreate-log assertions | Canonical comparison + complete-identity requirement + fail-closed snapshot | Low |
| R4 | **Rollback failure** — the original interface cannot be faithfully reconstructed after a failed transition | High (traffic loss until manual intervention) | Low with the fix; today Medium for IPv6 (snapshot would be empty) | `U-RB-*`, mocked failure scenarios, matrix rows 13–14 | Snapshot stores canonical family/endpoints/VNI/port plus MAC/MTU/addresses/bridge/admin state; completeness gate before any delete; exit-2 message retained | Low; manual recovery documented |
| R5 | **Underlay MTU** — 1450 default over an IPv6 path causes outer fragmentation (or breaks under fragment-hostile firewalls) | Medium (performance/interoperability, not silent corruption) | High if default unchanged (1500-byte paths are typical) | `U-MTU-*`; matrix row 19; packet capture during Phase 7 | Family-aware default (1450 v4 / 1430 v6), explicit `mtu` authoritative, documentation and capture evidence | Low |
| R6 | **Kernel/module compatibility** — an assumption that v6 VXLAN needs a kernel change, or a module rebuild that alters the tested payload | Medium | Very Low — v6 support verified in the shipped module; risk is process risk (someone rebuilding) | Hash pins in `scripts/validate-release.sh`; release diff review | Explicit "no module change" rule; hashes must remain `7c346342…` / `6d58ee59…`; no patch edits | Very Low |
| R7 | **Package compatibility / upgrade** — dependency version coupling (`edgeos-vxlan-kmod (= ${binary:Version})`) breaks an independent integration-package release | Medium | Medium if release mechanics are improvised | CI release validation; matrix rows 22–23 | Dual version bump with byte-identical module payload; validate existing v4 config after upgrade; installer pins updated only at release | Low |
| R8 | **Boot persistence** — IPv6 tunnel not restored because the underlay address (SLAAC/DHCPv6) is not ready when the config replays | Medium | Medium (timing dependent) | Phase 7 reboot rows (matrix 21) with the real underlay config | Existing boot flow (config loader + parent `end:` handler) is unchanged; verify ordering on hardware; document operational caveat if needed (e.g. underlay configured statically) | Medium until tested |
| R9 | **IPv6 canonicalization errors** — textual representations compared inconsistently | High if textually compared | Medium for naive implementations | `U-CANON-*`, `U-PARSE-*`, `U-IDEM-3` | Compare packed `inet_pton` bytes (canonical text is derived 1:1 from those bytes, so text equality is byte equality); one helper owns the logic | Very Low |
| R10 | **Unexpected-source packets** — treating `remote-ip` as an ingress allowlist | Medium (security expectation gap) | Medium (user misunderstanding) | Documentation review; matrix row 24; capture on hardware | Keep the README warning; add IPv6-specific `firewall ipv6-name` example verified against the firmware templates; repeat the packet test for v6 | Low, operational |
| R11 | **Engine default semantics** — removing the static MTU default interacts with how EdgeOS materialises defaults | Low–Medium (wrong MTU if mis-modelled) | Low (the static default is removed, but `node_exists mtu` is still consulted — see Q2) | Hardware check: configure v6 tunnel without `mtu`, verify live MTU 1430 and absence of a persisted `mtu` line | Compute the default in userspace; verify in Phase 1/7; if a stale persisted `mtu 1450` appears in old configs, document the one-line change | Low |
| R12 | **Test harness blind spots** — mocked tests pass while the real engine behaves differently (handler ordering, quoting) | Medium | Medium (engine not source-available here) | Phase 7 observes real commits; template diffs reviewed; helper invoked with literal-quoted args | Keep the mocked layer honest (assert command logs); treat hardware as the source of truth for engine behaviour; never derive "passed" status from mocks | Medium, bounded by Phase 7 |
| R13 | **Helper packaging** — new script omitted from the `.deb` or not executable | Low | Low | CI package-content check; `dpkg -c` output in the workflow | Add to `debian/edgeos-vxlan.install`; keep the release validator's package assertions | Very Low |
| R14 | **UDP checksums** — someone disables v6 checksums to make testing easier | Medium | Low | Code review of `create_vxlan` arguments; JSON `udp_zero_csum6_tx` on hardware | Defaults already compute checksums; plan forbids checksum options; document | Very Low |
| R15 | **Fragmentation/extension-header handling in firewalls** — outer fragments or extension headers bypass or are dropped unexpectedly | Medium, operational | Medium | Phase 7 capture + firewall test | Document MTU guidance and fragment treatment; verify with the native `ipv6-name` ruleset | Medium, operational |
| R16 | **Validation helper on the boot path** — the new helper runs during boot configuration replay (parent `commit:expression`, `local-ip` `syntax:expression`); a helper failure would abort a config load on a headless router | Medium | Low (helper consumes only literal arguments; core modules verified present on target) | Phase 7 reboot test (matrix row 21) + helper error-handling unit tests | Helper exits non-zero only for genuinely invalid input; dependencies limited to core `Socket`/`JSON::PP`; unit-test the exact argument forms the templates pass; a config that boot-replays was already accepted by the same checks at commit time | Low after Phase 7 |

## 2. Open questions and next evidence

| # | Question | Why it matters | Next evidence |
|---|---|---|---|
| Q1 | Exact target `ip -j -d link show` output for an IPv6 VXLAN | Parser contract and fixtures | Phase 1 capture (read-only + one-shot external test) |
| Q2 | Does the engine materialise `mtu` defaults in the active config after the template default is removed? | MTU correctness and `show configuration` expectations | Phase 1/7: configure without `mtu`, inspect `show configuration commands` and live MTU |
| Q3 | Exact engine ordering — commit-time validations vs node handlers, and `end:` vs leaf handlers | Confidence in the idempotency assumptions and in the no-side-effects claim for rejected commits | Phase 7 log observation plus a deliberate rejected commit (documented assumption today: `README.md:452–475`; the new parent `commit:expression` check assumes validations precede handlers) |
| Q4 | Boot ordering with dynamic IPv6 underlay addressing | Persistence | Phase 7 reboot test |
| Q5 | Does an IPv6 VXLAN produce new NSM/udev messages? | Noise assessment | Phase 7 `dmesg`/`logread` review |
| Q6 | Behaviour of `brctl` cost/priority for a v6-underlay VXLAN | Bridge parity | Phase 7 bridged test |
| Q7 | Is the `commit:expression` helper invocation style safe on the target engine for values with `%`, `:`, `/`? | Validation robustness | Unit tests plus a Phase 7 validation attempt with unusual-but-valid literals; note that `$VAR(@)` expansion was the subject of an earlier fix (`b806c29`) |
| Q8 | Should an upgrade normalize previously stored non-canonical IPv6 endpoint strings in `config.boot`? | One-time churn risk | Design says no (canonicalization is internal); confirm no engine-side comparisons depend on stored spelling |

## 3. Explicitly out of scope for this feature (recorded, not planned)

EVPN/control-plane integration; multicast VXLAN; multipoint/multi-VTEP; VLAN-to-VNI mapping; FDB management; hardware offload; other EdgeRouter models; other EdgeOS releases; language or packaging-model migration. Any discovery during implementation that would touch these belongs in a separate issue.
