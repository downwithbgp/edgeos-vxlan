The emulated-engine harness copies the candidate `src/vyatta-vxlan`, `src/vyatta-vxlan-firewall`,
`src/vyatta-vxlan-addr`, `src/vyatta-vxlan-bridge`, `src/Interface.pm` and
`templates/interfaces/vxlan` into the extracted firmware root, then runs the vendor configuration
engine under `qemu-mipsel-static`. Because the firmware's MIPS `iptables` cannot speak the host
kernel's x86_64 netfilter ABI, `/sbin/iptables`, `/sbin/ip6tables` and their `-save`/`-restore`
forms are replaced with wrappers around the host's `iptables-legacy` binaries with
`XTABLES_LIBDIR=/x86/usr/lib/x86_64-linux-gnu/xtables`. `/run/vyatta/vyatta_fw_trees` and
`/run/vyatta/vyatta_fw_stateful` are seeded because the container's `/run` is bind-mounted over the
firmware root's `/run`. `modprobe` is a no-op: the host already has `vxlan`, `udp_tunnel` and
`ip6_udp_tunnel` loaded.

## 3. Emulated EdgeOS configuration-engine rerun

The engine was started from a fresh configuration state for each sequence. The three commits used a
`vxlan42` interface with a fixed local/remote VTEP and:

* **A** — `in { name VXLAN_IN; ipv6-name VXLAN6_IN }` and `local { ipv6-name VXLAN6_IN }`, with
  `VXLAN_IN` and `VXLAN6_IN` at `default-action drop` and one ICMP/ICMPv6 accept rule.
* **B** — replaced the attachments with `VXLAN_IN2`/`VXLAN6_IN2` at `default-action accept`; the
  original rulesets remained configured (so the rewrite did not depend on deleting a referenced
  chain).
* **C** — removed the `firewall` attachments while keeping the rulesets and the interface.

| Commit | Loader result | Observed evidence |
|---|---|---|
| A | `LOADER_RC=0`, `commit succeeded` | `-A VYATTA_FW_IN_HOOK -i vxlan42 -j VXLAN_IN`; `-A VXLAN_IN -m comment --comment "VXLAN_IN-10000 default-action drop" -j DROP`; IPv6: `-A VYATTA_FW_IN_HOOK -i vxlan42 -j VXLAN6_IN`, `-A VYATTA_FW_LOCAL_HOOK -i vxlan42 -j VXLAN6_IN`, `-A VXLAN6_IN -m comment --comment "VXLAN6_IN-10000 default-action drop" -j DROP` |
| B | `LOADER_RC=0`, `commit succeeded` | dispatch replaced: `-A VYATTA_FW_IN_HOOK -i vxlan42 -j VXLAN_IN2`; terminal rule `-A VXLAN_IN2 -m comment --comment "VXLAN_IN2-10000 default-action accept" -j RETURN`; IPv6 `VXLAN6_IN2` in both `VYATTA_FW_IN_HOOK` and `VYATTA_FW_LOCAL_HOOK`, same `RETURN` terminal rule |
| C | `LOADER_RC=0`, `commit succeeded` | no `-A VYATTA_FW_*_HOOK -i vxlan42` line remains; the target chains remain; the engine issued `--delete VYATTA_FW_IN_HOOK 1` and `--delete VYATTA_FW_LOCAL_HOOK 1` |

Representative excerpts from the run:

```text
# commit A
-A VXLAN_IN -m comment --comment "VXLAN_IN-10000 default-action drop" -j DROP
-A VYATTA_FW_IN_HOOK -i vxlan42 -j VXLAN_IN

# commit B
-A VXLAN_IN2 -m comment --comment "VXLAN_IN2-10000 default-action accept" -j RETURN
-A VYATTA_FW_IN_HOOK -i vxlan42 -j VXLAN_IN2

# commit C (dispatch removed; chain retained)
-N VXLAN_IN2
-A VXLAN_IN2 -p icmp -m comment --comment VXLAN_IN2-10 -j RETURN
-A VXLAN_IN2 -m comment --comment "VXLAN_IN2-10000 default-action accept" -j RETURN
```

After each commit the JSON interface view was correct: `info_kind: vxlan`, `id: 42`,
`local: 127.0.0.1`, `remote: 127.0.0.2`, `port: 4789`, and the interface was up (`0x1003`). The
human `ip -d link` output remains the known-broken format in the emulation; the helper uses
`ip -j -d link show`, which is correct.

The key RC3 validation is that the new terminal-rule parser accepted the vendor's real rule,
including the quoted comment with spaces and the verdict mapping: `drop` -> `DROP` (commit A) and
`accept` -> `RETURN` (commit B), with the configured action matching the comment. The dispatch
replacement and removal committed successfully through the candidate reconciler and helper.

## 4. What this evidence proves and does not prove

**Proves:**

* the network-namespace suite passes on the candidate commit;
* the candidate helper's terminal-default parser and configured-action comparison accept the
  vendor's real default-action rule for both `drop` and `accept`;
* the candidate scripts apply, replace and remove the dispatch through the real vendor
  configuration-engine path;
* the interface survived the replacement without recreation and the JSON live-state view remained
  correct.

**Does not prove:**

* the MIPS `iptables` netlink ABI (the harness uses x86_64 `iptables-legacy` wrappers);
* kernel module loading (host modules are reused; `modprobe` is a no-op);
* the EdgeOS 4.14 kernel dataplane or any hardware dataplane;
* external Route64 connectivity or reboot behaviour (still hardware acceptance items);
* the static-ruleset case: the emulation's known static-ruleset limitation was avoided by starting
  from fresh engine state and adding/changing the rulesets in the same commit as the attachment.
