# v0.3.0 — Platform investigation

**Status:** investigation complete for the supported platform. Items marked *inferred* still require the
hardware acceptance procedure in `v0.3.0-hardware-acceptance.md`.

This document records what was actually inspected, what was observed, and what is only an inference.
The firmware artifact examined is the official `ER-e50.v3.0.1.5862409.tar` image:

```text
SHA-256 e3d3fe0697bc01d8d9347f3df2b38ce093c2db69f6fa8ea65170270d59a8fb3d
Version: v3.0.1.5862409.250924.1407
SquashFS: 4.0, xz, 71,742,201 bytes
```

The image was unpacked and its installed configuration templates, `ubnt-fw` binary, firewall helper
scripts, `Vyatta::Interface`, `my_cli_shell_api`, `my_commit`, and boot loader were examined directly.
Selected binaries were also executed under `qemu-mipsel-static` against the host kernel to reproduce
the `ip -d` reporting defect.

## 1. Native interface firewall architecture

### 1.1 Configuration templates

EdgeOS 3.0.1 installs per-interface-type firewall attachment templates. There is **no** generic
`interfaces/node.tag/firewall` tree; each interface type that supports firewall attachment has its own
copy. For example:

```text
/opt/vyatta/share/vyatta-cfg/templates/interfaces/ethernet/node.tag/firewall/in/name/node.def
/opt/vyatta/share/vyatta-cfg/templates/interfaces/ethernet/node.tag/firewall/local/ipv6-name/node.def
```

The installed leaves follow the same form (ethernet, bonding, bridge, pseudo-ethernet, tunnel, vti,
wireguard, wirelessmodem, ...):

```text
type: txt
allowed: local -a params
        eval "params=($(cli-shell-api listActiveNodes firewall name))"
        echo -n "${params[@]}"

update: ifname=$VAR(../../../@)
        /usr/sbin/ubnt-fw update-interface update $ifname in $VAR(@) name

delete: ifname=$VAR(../../../@)
        /usr/sbin/ubnt-fw update-interface delete $ifname in $VAR(@) name
```

The equivalent `ipv6-name` leaves pass `ipv6-name` as the last argument. The installed `vti` and
`wireguard` trees are complete examples of the same shape for a routed virtual interface.

Consequences:

* A new interface type must ship its own `firewall/{in,out,local}/{name,ipv6-name}` template subtree.
  There is no vendor template to inherit from at runtime.
* The vendor engine does not validate ruleset existence in the leaf; `ubnt-fw` does that when the
  action runs. v0.3.0 adds a configuration-time check so an invalid reference fails before any
  interface or dataplane mutation.
* `priority` is absent throughout the vendor firewall subtrees. The v0.3.0 subtree must preserve that
  property: the commit engine groups changes by declared priority, and a priority-less subtree stays
  with its parent. This is what makes a failed firewall action and the vxlan reconciler one commit
  unit instead of two independently committed units.

### 1.2 `ubnt-fw` (the EdgeOS firewall engine)

EdgeOS 3.0.1 does **not** use the historical Vyatta `vyatta-firewall.pl`. The installed binary is
`/usr/sbin/ubnt-fw` (MIPS ELF, package `vyatta-cfg`, version
`1:1.0.18+t5862406.er.3.0.1.ef8cbcb`). It preserves the Vyatta hook-chain model:

* `VYATTA_FW_IN_HOOK` (FORWARD, `-i`),
* `VYATTA_FW_OUT_HOOK` (FORWARD, `-o`),
* `VYATTA_FW_LOCAL_HOOK` (INPUT, `-i`),
* ruleset chains named after the configured `firewall name` / `firewall ipv6-name`.

The `update-interface` action:

1. checks that the referenced ruleset exists in the configuration (working configuration, including
   nodes added by the current commit);
2. rejects a per-interface firewall on an interface that belongs to a zone;
3. rejects attachment to a switch-port interface;
4. finds the existing jump for that interface and direction in the hook chain and replaces it, or
   inserts a new jump at position 1;
5. uses `iptables` for `firewall name` and `ip6tables` for `firewall ipv6-name`.

The `delete` action removes the jump for the interface and direction. A ruleset that is still
referenced by a jump cannot be deleted: `ubnt-fw` refuses the chain deletion.

Observed directly under `qemu-mipsel-static`:

```text
# no ruleset configured
ubnt-fw update-interface update vxlan42 in FOO name
Firewall config error: Rule set FOO is not configured      (exit 1)

# with a configured ruleset the same call proceeds to the iptables work
```

The binary has no interface-type table and no dependency on `Vyatta::Interface`. Its only
interface-shape checks are the zone and switch-port checks above. In particular, a name matching
`^vxlan[0-9]+$` is accepted by the same code path as `vti`/`wireguard`; no vendor patch to `ubnt-fw`
is required. This is *observed* for the validation path and *inferred* for the iptables path; the
hardware acceptance procedure exercises the complete path on the real router.

### 1.3 `Vyatta::Interface`

The firmware's `Vyatta::Interface` is byte-for-byte identical to the GPL source copy already used by
this project. The package diverts it and adds one mapping:

```perl
'^vxlan[\d]+$' => { path => 'vxlan' },
```

This mapping is **not** used by `ubnt-fw` (a C++ binary using `libvyatta-cfg`), but it remains required
by other Vyatta consumers (the CLI/config system, address handling, and any subsystem that maps a
device name to a configuration path). It must stay in the diverted file.

### 1.4 Firewall configuration tree

`firewall name` and `firewall ipv6-name` are tag nodes at priority 210 inside the `firewall` root
(priority 199). The root's `create:` action initializes the base hook chains via
`firewall.init start ubnt-fw`; each ruleset tag's `end:` action calls
`ubnt-fw update-rules <family> <name>` to build or update its chain.

The base hook chains are initialized idempotently: `firewall.init start` returns immediately if
`VYATTA_PRE_DNAT_HOOK` already exists. It does not flush user chains on a normal boot.

### 1.5 Commit ordering and partial commits

The engine's behaviour is already documented from the vendor source in
`docs/issue-3-partial-commit-analysis.md`: changes are split into priority subtrees, each subtree is
validated and executed independently, and `commitConfig()` writes the successfully marked subtrees
even when another subtree failed. A commit is therefore **not** an atomic transaction.

For this release the relevant consequences are:

* `firewall` (199) is committed before the `interfaces` root (default 200), so the base hook chains and
  ruleset chains exist before interface attachments are installed (*inferred from the priorities; the
  hardware acceptance test checks the boot path*).
* Interface children without their own `priority` are executed before the interface's `end:` action,
  and share the interface subtree's commit result. The vxlan reconciler is the `end:` action. This is
  why the firewall subtree must not declare a priority.
* `mtu`, `address` and `bridge-group` already have their own priority 460 subtrees. That is existing
  behaviour and is not changed by v0.3.0.
* A failed firewall leaf action can still be followed by the parent `end:` action if the engine
  continues executing the subtree. The reconciler must therefore not rely on the engine to stop at a
  failed child. It verifies the effective attachments before bringing the interface up.

## 2. `ip -d link show` reporting defect

### 2.1 Reproduction

The firmware's `/sbin/ip` is `iproute2-ss171113` (a 4.14-era build). Running it under
`qemu-mipsel-static` against a live VXLAN device on the host kernel produced:

```text
vxlan-probe: ... promiscuity 1432079556
    vxlan id 1432114088 remote 127.0.0.2 local 127.0.0.1 srcport 0 0
    dstport 1432123540 ageing 1432123684 ...
    numtxqueues 1432079772 numrxqueues 1432079804
    gso_max_size 1432079836 gso_max_segs 1432079872
```

The same binary with `-j -d` produced the correct JSON:

```json
"id": 5002,
"remote": "127.0.0.2",
"local": "127.0.0.1",
"port": 4789,
"ageing": 300,
"num_tx_queues": 1,
"num_rx_queues": 1,
"gso_max_size": 65536,
"gso_max_segs": 65535
```

The defect is not VXLAN-specific and not in the kernel: `ip -d link show dev lo` and `dev eth0`
show the same garbage for `promiscuity` and every later integer attribute, while `ip -j -d` on the
same devices is correct.

### 2.2 Cause

The vendor's `ip` build uses the generic `print_uint(enum output_type, key, fmt, uint64_t value)`
helper. `print_uint` calls the variadic `color_fprintf(stdout, color, fmt, value)` with a 64-bit
value. Under the MIPS o32 ABI used by this firmware, the 64-bit variadic argument is misaligned
relative to the callee's `va_list`, so the human-readable `%u` path prints a pointer (the values are
addresses in the PIE image) instead of the integer. The JSON path calls
`jsonw_uint_field(..., uint64_t)` directly and is unaffected.

This is a stock iproute2/toolchain defect in the firmware, not project integration code and not kernel
attribute generation. Rebuilding or replacing the platform's complete iproute2 package is out of
scope.

### 2.3 Effect on the reconciler

The reconciler reads live state with:

```text
ip -j -d link show dev "$INTERFACE"
```

and parses the JSON. It never parses the human-readable `-d` output. The defect therefore cannot
influence identity comparisons, snapshots, rollback or lifecycle decisions. v0.3.0 adds a regression
test that keeps the reconciler on the JSON path and documents `ip -j -d` as the trustworthy
diagnostic.

## 3. Bridged VXLAN

The project supports a VXLAN interface as a bridge port. On Linux, a frame forwarded by the bridge
between two ports is **not** seen by the routed `FORWARD` chain with `-i <port>`; with bridge netfilter
the logical input interface is the bridge device, and enabling `br_netfilter` changes the handling of
all bridged IPv4/IPv6 traffic on the router. Attaching `interfaces vxlan vxlan42 firewall in ...` to a
bridge port would therefore appear to configure enforcement while the L2-forwarded dataplane remains
unfiltered.

v0.3.0 rejects firewall attachments on an interface that is a bridge member, in both directions of the
configuration transition:

* adding a firewall attachment to a bridged VXLAN interface fails configuration validation;
* adding `bridge-group bridge` to a VXLAN interface that already has firewall attachments fails
  validation.

No global bridge-netfilter setting is enabled. Routed VXLAN operation is the primary supported case.
Bridged L2 firewall enforcement is explicitly out of scope for v0.3.0.

## 4. Checksum offload evidence

The Route64 deployment initially showed invalid UDP checksums in local `tcpdump` captures. Disabling
generic TX checksum offload changed the capture, not connectivity. The actual fault was an incorrect
VNI; after correcting the VNI and restoring offload, bidirectional VXLAN worked. This is consistent
with checksum offload being a capture artifact, not a dataplane defect. No kernel or offload change is
introduced. Interoperability testing keeps TX offload enabled by default and treats checksum warnings
in local captures as non-authoritative.

## 5. Evidence classification

| Claim | Basis |
|---|---|
| Interface firewall templates are per interface type and call `ubnt-fw update-interface` | Observed in the installed rootfs |
| `ubnt-fw` accepts `vxlanN` names and has no interface-type mapping | Observed validation path; inferred for the full iptables path |
| The firewall root initializes hook chains before interfaces | Inferred from template priorities and the vendor commit algorithm; hardware test required |
| Firewall leaves without a priority share the interface subtree | Inferred from the vendor commit algorithm and the existing `description` leaf behaviour; emulated-engine test and hardware test required |
| `ip -d` human output is broken while `-j -d` is correct | Observed under qemu against the host kernel |
| Dispatch survives netdevice recreation with the same name | Inferred from iptables matching by name; hardware/namespace test required |
| Bridged L2 traffic is not covered by a port attachment | Linux bridge-netfilter behaviour; hardware test required for the exact EdgeOS path |
| Commit is non-atomic | Already established from the vendor source in `docs/issue-3-partial-commit-analysis.md` |

## 6. Open questions for hardware acceptance

1. Does a cold boot commit install the interface dispatches before the VXLAN interface is brought up,
   and is there any observable fail-open interval?
2. Does `ubnt-fw update-interface` succeed for `vxlanN` on the real MIPS userspace/kernel?
3. Does the dispatch survive the project's delete/recreate cycle with the same interface name?
4. What happens on a policy replacement, a policy rename, and a ruleset deletion while attached?
5. Does `commit-confirm` rollback restore both the interface and its firewall attachment?
6. Does package upgrade from v0.2.2 preserve existing unfiltered VXLAN behaviour?
7. Does package removal refuse to leave a live VXLAN interface without its integration?
8. Do IPv6 NDP and essential ICMPv6 continue to work under an operator IPv6 policy attached to the
   overlay?
