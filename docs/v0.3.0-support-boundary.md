# v0.3.0 — supported configuration workflows and security contract

**Scope:** this record defines which configuration workflows this package supports on EdgeOS 3.0.1,
what its verification guarantees, and where the platform's own behaviour limits them. It is based on
hardware evidence from the ER-X (2026-11-26); the underlying platform defect is recorded in
`docs/v0.3.0-edgeos-scripted-commit-limitation.md`.

## 1. What the package verifies

Before an interface is made operational with its configured attachments, and for every
`--verify-all`, the helper checks each configured `in`/`out`/`local` attachment (IPv4 and IPv6):

* the configured ruleset exists in the configuration and its name is valid;
* the effective chain exists and is non-empty;
* it ends in the vendor's unconditional terminal default-action rule, and the engine's verdict
  matches the configured default action;
* **every configured rule number is present in the effective chain** (vendor `<chain>-<n>` comment
  format). An unreadable rule list is a configuration-API failure, never "no rules";
* exactly one exact dispatch exists in the correct hook, the hook is reachable from the base chain,
  and no same-interface or unconditional rule shadows it.

A failure restores the pre-change dispatch where possible and leaves the interface down. The
verification is bounded to the vendor's documented output formats; it does not re-implement the
vendor's policy engine.

## 2. Workflow support boundary

| Workflow | Status | Procedure |
|---|---|---|
| Interactive firewall ruleset creation/modification | **Supported** | Use the CLI (`configure … commit`). The platform applies rulesets correctly in this path. |
| Scripted firewall ruleset creation/modification | **Not supported** | EdgeOS 3.0.1 can silently reduce the ruleset to its default action, or fail the commit, when a scripted (script-template) session applies a `firewall name` change. Do not use automation for this. |
| Scripted VXLAN configuration referencing existing, correctly materialized rulesets | **Supported** | Attachment-only changes are safe; the gate verifies the referenced chains, including rule presence. |
| Ruleset creation and attachment in one commit | **Interactive only** | Create and attach in one interactive commit. A scripted combined commit fails closed (the ruleset is not yet materialized when the interface hook runs). |
| Configuration restoration at boot | **Verified on the RC5-qualified build** | The RC5 hardware qualification restored the native rulesets, all four dispatches and the interface after reboot. The earlier pending state is superseded by that record; see [v0.3.0-hardware-qualification-report.md](v0.3.0-hardware-qualification-report.md). |
| Commit-confirm and rollback | **Supported, interactive** | Use an interactive session for the policy change; after a rollback, re-run `--verify-all` and confirm the previous ruleset contents, not only the default action. |

Because the platform defect reproduces with pure `firewall name` configuration and no VXLAN
involvement, the same limitation applies to stock interfaces and native attachments; it is not
introduced by this package. This package does not patch the vendor firewall.

## 3. Operational procedures

1. Treat firewall ruleset changes as interactive-only on EdgeOS 3.0.1.
2. When automation must prepare a ruleset, create it **and** attach it in one interactive commit,
   or create it interactively first and verify its effective chain before any attachment.
3. After any non-interactive configuration load or restoration, run
   `vyatta-vxlan-firewall --verify-all <interface>` inside a configuration session. The gate now
   rejects a chain that lost configured rules.
4. A ruleset edited by a scripted commit can be degraded before the next interface apply. The next
   `--apply`/`--verify-all` detects the missing rules and fails closed; do not treat the absence of
   an error at the ruleset-only commit as proof of enforcement.
5. Keep the platform limitation in the operational record; if a later firmware fixes it, re-run the
   interactive/scripted matrix and retire this boundary.

## 4. Residual exposure

The package observes the interface apply and its own `--verify-all`; it cannot observe a ruleset-only
scripted commit. A degraded attached ruleset therefore remains in effect until the next interface
apply or explicit verification. This is a platform-level exposure that affects native attachments
equally. The supported boundary above is the mitigation: do not change firewall rulesets from
scripted sessions.
