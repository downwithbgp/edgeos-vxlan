# v0.3.0 hardware acceptance procedure

**Status:** procedure prepared; **not executed**. No hardware was changed, rebooted, upgraded or
installed by the implementation work.

**Purpose:** establish that native firewall attachments on a routed VXLAN interface enforce the
intended policy in the dataplane across the supported lifecycle, and that no operational-but-unfiltered
interval can be observed.

**Supported platform:** Ubiquiti EdgeRouter X / ER-e50, EdgeOS 3.0.1 build 5862409, Linux
4.14.54-UBNT, MIPS little-endian.

**Evidence classes:** PASS requires dataplane evidence (probe logs, counters, captures), not merely a
configuration that looks correct. Steps are marked:

* **N — non-disruptive:** no production interface, policy or traffic change.
* **D — disruptive:** touches the production tunnel or its traffic; maintenance window required.
* **X — destructive:** deletes/recreates an interface or package; isolated or lab unit preferred.
* **R — reboot:** cold boot; requires console access and runtime-route restoration.

**External-host dependency:** the OCI test host is currently unavailable. Independent Internet-facing
positive/negative tests are marked **DEFERRED — external host required**. Local-underlay and
router-originated tests can proceed; they are not equivalent.

## 0. Safety, access, and preconditions

* Use a **disposable test router** for the destructive phases where possible. The production ER-X may
  be used for the isolated-interface phases only if a new VXLAN interface and its policy do not affect
  production traffic.
* Do not run production-migration, reboot, package-removal or failure-injection steps without the
  maintainer's explicit approval and a maintenance window.
* **Management path must not depend on `vxlan41913`.** Use a physical/VLAN management address or the
  console. Test the path before starting.
* Have a **console** (serial or local) available for the production migration and reboot. Do not rely
  on SSH over the tunnel.
* Have a **local VTEP peer** for the isolated tests: a Linux host on the underlay with the VXLAN
  module, or a second disposable router. The OCI host is not required for this; a local host is
  sufficient for the dataplane semantics.
* Take a full configuration backup, a copy of `/config/config.boot`, and an off-router copy of
  `iptables-save`/`ip6tables-save`, `ip -6 rule`, and `ip -6 route` output before any change.
* Record the package versions, the diverted `Vyatta::Interface.pm` hash, and the kernel module hashes.
* Use documentation address ranges in any evidence published outside the maintainer's environment.

## 1. Production-specific inventory (N)

The operational Route64 interface is `vxlan41913`. It currently has:

* manually installed IPv6 INPUT/FORWARD jumps to `HEv6_LOCAL` and `HEv6_IN`;
* interface-scoped IPv4 INPUT/FORWARD DROP rules;
* runtime-only IPv6 policy-routing rules and a dedicated routing table for the Route64 allocation.

The manual rules can **mask** a failure of native enforcement. Capture them and their positions
exactly:

```bash
sudo iptables-save -t filter > /config/vxlan41913-pre.v4
sudo ip6tables-save -t filter > /config/vxlan41913-pre.v6
sudo iptables -S | grep -E 'vxlan41913|HEv6'
sudo ip6tables -S | grep -E 'vxlan41913|HEv6'
sudo iptables -S INPUT FORWARD
sudo ip6tables -S INPUT FORWARD
sudo iptables -S VYATTA_FW_IN_HOOK VYATTA_FW_OUT_HOOK VYATTA_FW_LOCAL_HOOK
sudo ip6tables -S VYATTA_FW_IN_HOOK VYATTA_FW_OUT_HOOK VYATTA_FW_LOCAL_HOOK
```

Record the **rule order** of `INPUT` and `FORWARD`, not just the rule text. The native dispatch is
installed inside the `VYATTA_FW_*` hooks; if a manual rule sits before the hook that jumps to those
chains, it can shadow the native policy. If the manual rules are after the hook, they are redundant
but still mask counters.

Capture the runtime policy routing separately; it is **not** owned by `edgeos-vxlan`:

```bash
ip -6 rule show > /config/route64-rules-pre.txt
ip -6 route show table all > /config/route64-routes-pre.txt
ip -6 route show table <ROUTE64_TABLE> > /config/route64-table-pre.txt
```

Record the table number and the exact `ip -6 rule add ...` and `ip -6 route add ... table <N>` commands
needed to restore them. These rules are runtime-only and a reboot will remove them.

## 3. Isolated native attachment and dataplane (N for production; D for the test peer)

Use a disposable routed interface `vxlan903` with a local VTEP peer. Do not attach anything to
`vxlan41913` in this phase.

```text
configure

set interfaces vxlan vxlan903 vni 903
set interfaces vxlan vxlan903 local-ip <underlay-local>
set interfaces vxlan vxlan903 remote-ip <local-peer>
set interfaces vxlan vxlan903 port 4789
set interfaces vxlan vxlan903 mtu 1450
set interfaces vxlan vxlan903 address 198.51.100.1/24
set interfaces vxlan vxlan903 address 2001:db8:903::1/64

set firewall name VXLAN903_IN default-action drop
set firewall name VXLAN903_IN rule 10 action accept
set firewall name VXLAN903_IN rule 10 protocol icmp
set firewall name VXLAN903_IN rule 20 action accept
set firewall name VXLAN903_IN rule 20 state established enable
set firewall name VXLAN903_IN rule 20 state related enable

set firewall ipv6-name VXLAN903_IN6 default-action drop
set firewall ipv6-name VXLAN903_IN6 rule 10 action accept
set firewall ipv6-name VXLAN903_IN6 rule 10 protocol icmpv6
set firewall ipv6-name VXLAN903_IN6 rule 20 action accept
set firewall ipv6-name VXLAN903_IN6 rule 20 state established enable
set firewall ipv6-name VXLAN903_IN6 rule 20 state related enable

set interfaces vxlan vxlan903 firewall in name VXLAN903_IN
set interfaces vxlan vxlan903 firewall in ipv6-name VXLAN903_IN6

commit
```

| Step | Test | Pass criterion |
|---|---|---|
| 3.1 | `show configuration commands \| grep vxlan903` | attachments present |
| 3.2 | `show firewall name VXLAN903_IN`; `show firewall ipv6-name VXLAN903_IN6` | rulesets present |
| 3.3 | `sudo iptables -S VYATTA_FW_IN_HOOK` | exactly one `-i vxlan903 -j VXLAN903_IN` jump |
| 3.4 | `sudo ip6tables -S VYATTA_FW_IN_HOOK` | exactly one `-i vxlan903 -j VXLAN903_IN6` jump |
| 3.5 | IPv4 echo from the local peer | permitted; counters increase |
| 3.6 | IPv4 TCP/UDP to a denied port | dropped; counters increase |
| 3.7 | IPv6 NDP and ICMPv6 echo | neighbour resolution works; echo permitted |
| 3.8 | IPv6 TCP to a denied port | dropped |
| 3.9 | Traffic on the underlay (outer UDP/4789) | untouched by the overlay attachment |
| 3.10 | Traffic on an unrelated interface policy | unchanged |
| 3.11 | `sudo /opt/vyatta/sbin/vyatta-vxlan-firewall --status vxlan903` **inside a configuration session or commit context** | configured and effective pairs match |

Repeat 3.1–3.10 for `local` and `out`; `out` must be tested with **forwarded** traffic, not traffic
originated by the router.

### Effective-state negative checks (unit-verified, confirm on hardware)

While `vxlan903` is up, verify that the gate rejects a manipulated dispatch. On the isolated
interface only:

1. Insert a duplicate hook rule with `sudo iptables -A VYATTA_FW_IN_HOOK -i vxlan903 -j VXLAN903_IN`;
   run a commit that touches `vxlan903` (for example a description change) in a **non-production
   window**. The commit must fail and the interface must be taken down or remain down; remove the
   duplicate and re-commit.
2. Insert a global `-j DROP` rule **before** the vxlan903 jump; repeat. The gate must report a shadowed
   dispatch and the interface must not be operational.
3. Empty the `VXLAN903_IN` chain (isolated interface only); the gate must report an empty chain and
   the interface must not be operational.

These tests prove the strict gate on the real `iptables -S` output. Do not run them on `vxlan41913`.

## 4. Destructive lifecycle on the isolated interface (X, isolated only)

| Step | Action | Pass criterion |
|---|---|---|
| 4.1 | Replace `VXLAN903_IN` with `VXLAN903_IN_B` | commit succeeds; jump replaced; no netdevice recreation (ifindex unchanged); counters increase for the new chain |
| 4.2 | Delete the attachment | jump removed; interface still up; unrelated rules unchanged |
| 4.3 | Add a second isolated VXLAN sharing the ruleset | both jumps present; deleting one leaves the other |
| 4.4 | Change an unrelated ruleset/interface policy | vxlan903 jump unchanged; no recreation |
| 4.5 | `disable` then enable vxlan903 | down with jump present; up with jump present; gate passes |
| 4.6 | Delete the attached ruleset while attached | commit fails with a “still in use” error; jump remains |
| 4.7 | Rename a ruleset and update the attachment in one commit | commit succeeds with the new chain, or fails without leaving the interface unprotected; record exact behaviour |
| 4.8 | `commit-confirm` with a policy change and no confirm | rollback restores the previous policy and interface state |
| 4.9 | Change VNI, UDP port, remote-IP in turn | interface recreated; jump survives (name-based); no negative-probe success |
| 4.10 | Change VNI and attachment in one commit | new jump installed; no negative success |
| 4.11 | Failure injection (Phase 5) | old state restored or interface down; explicit error |

Use a continuous negative probe during 4.9–4.11. The ifindex must change while the jump remains.

## 5. Failure injection (X, isolated interface only)

All injections must be reversible and performed on the isolated `vxlan903` with approval. Record exact
commands.

1. **Invalid ruleset reference.** Set an attachment to a nonexistent ruleset. The commit must fail at
   validation before any mutation; the old jump and interface are unchanged.
2. **Attachment install failure.** Replace `/usr/sbin/ubnt-fw` with a wrapper that exits 1 for
   `update-interface` and delegates everything else. Add a new attachment. Commit must fail; the
   interface must not be operational without the attachment; the error names the interface and
   attachment. Restore `ubnt-fw`.
3. **New attachment on an up interface.** With a wrapper as above, attach a new direction on an
   already-up `vxlan903`. The old (empty) dispatch must be restored and the interface taken down.
4. **Recreation failure with an attachment change.** Change the VNI and add a 256-character
   description in one commit. The interface must roll back to the old identity and the old jump; if
   restoration fails, the interface must be down.
5. **Rollback failure.** Make both creation and restoration fail (for example block the `vxlan`
   module load after deletion, with a controlled test). The interface must be down, the error
   explicit, and no traffic forwarded.
6. **Verification failure.** Replace `iptables`/`ip6tables` with a wrapper that makes `-C` fail after a
   successful `ubnt-fw update`. The commit must fail and the interface must be down.
7. **Strict gate checks.** Repeat the duplicate/shadow/empty-chain manipulations from Phase 3.

After each injection: restore the original files, re-commit, and verify convergence. Do not leave a
wrapper in place.

## 6. Production migration of `vxlan41913` (D)

**Precondition:** Phases 3–5 pass on the isolated interface, and the maintainer has approved the
maintenance window. Console access is available. The full `iptables-save`/`ip6tables-save` backups
and the exact manual-rule list are off-router.

The goal is to attach native policy **before** removing the manual rules, verify the native path, and
then remove the manual rules one at a time. Do not remove all manual rules in one step.

### 6.1 Create the native policy

Translate the intended manual policy into native rulesets. Do not blindly copy the manual chain
contents; review the intent:

* `HEv6_LOCAL_NATIVE` — router-destined IPv6: NDP/ICMPv6 essentials, established/related, explicit
  management, intended default action.
* `HEv6_IN_NATIVE` — forwarded IPv6: intended allow/deny, established/related, default action.
* `VXLAN41913_IN4` — inner IPv4: default drop for the IPv6-only transit deployment, or the intended
  IPv4 policy if that changes.

Attach them to `vxlan41913` **without removing the manual rules**:

```text
set interfaces vxlan vxlan41913 firewall in ipv6-name HEv6_IN_NATIVE
set interfaces vxlan vxlan41913 firewall local ipv6-name HEv6_LOCAL_NATIVE
set interfaces vxlan vxlan41913 firewall in name VXLAN41913_IN4
commit
```

At this point both the manual rules and the native jumps are present. **The native path may be masked
by the manual rules.** Do not proceed until the native path is proven effective.

### 6.2 Prove the native path

1. Inspect order:
   ```bash
   sudo ip6tables -S INPUT FORWARD
   sudo ip6tables -S VYATTA_FW_IN_HOOK VYATTA_FW_LOCAL_HOOK
   sudo iptables -S INPUT FORWARD
   sudo iptables -S VYATTA_FW_IN_HOOK
   ```
   Locate the `VYATTA_FW_*` hook jump relative to the manual `HEv6`/`vxlan41913` rules.
2. Zero the native chain counters (`sudo ip6tables -Z HEv6_IN_NATIVE`, etc.), send a permitted and a
   denied test probe from the local underlay host to the Route64 overlay addresses, and check that
   the **native chain** counters increase. If the native chain counters do not increase, the manual
   rules are shadowing the native path: stop and do not remove the manual rules.
3. Verify `ip6tables -S VYATTA_FW_IN_HOOK` has exactly one `-i vxlan41913 -j HEv6_IN_NATIVE` jump and
   `VYATTA_FW_LOCAL_HOOK` has the local jump; `iptables` has the IPv4 `in`/`local` jumps.
4. Run a negative probe against a denied native rule and confirm it is dropped **and** counted in the
   native chain.

If any of these fail, detach the native attachments and restore the prior state; do not remove the
manual rules.

### 6.3 Remove the manual rules one at a time

Preserve the exact commands. For each manual rule:

1. Delete **one** rule (the exact `iptables -D`/`ip6tables -D` command from the backup).
2. Immediately verify:
   * the native chain counters still increase;
   * the permitted local probe still passes;
   * the denied local probe still fails;
   * the management path is unaffected.
3. If anything regresses, re-add that single rule from the backup (`-I` at its original position) and
   stop.

Remove the IPv4 DROP rules only after `VXLAN41913_IN4` is attached and its counters prove the native
IPv4 path. Remove the IPv6 INPUT/FORWARD jumps only after the native IPv6 chains are proven.

Finally, confirm no manual `HEv6`/`vxlan41913` rules remain in `INPUT`/`FORWARD`; the only dispatch
should be the native `VYATTA_FW_*` jumps. Keep the backup files.

## 7. Cold boot and fail-open detection (R, D)

The external OCI probe host is unavailable. The **Internet-facing** continuous negative probe is
**DEFERRED — external host required**. A local probe on the underlay/overlay can still be run and is
required; it does not cover the Internet path.

Before the reboot:

1. Save the configuration.
2. Save the runtime policy routing commands and table (`ip -6 rule`, `ip -6 route show table <N>`).
3. Start the local probe that must be denied (for example IPv6 TCP/8080 to an overlay address), at
   100 ms, logging timestamps.
4. Have the console ready.

| Step | Action | Pass criterion |
|---|---|---|
| 7.1 | Cold boot | no successful denied probe; after boot the interface is up and the native jump is present |
| 7.2 | Reapply the runtime Route64 policy-routing rules/table immediately | `ip -6 rule` and `ip -6 route show table <N>` match the pre-boot capture |
| 7.3 | Inspect the boot/commit logs | no firewall attachment error; if there is one, the interface is down |
| 7.4 | `show configuration commands`, `show interfaces`, `ip -j -d link show`, native chain counters | configuration and effective state agree |
| 7.5 | Repeat the boot with the local probe started before the router finishes booting | same; record any successful denied probe (must be none) |
| 7.6 | External probe from the OCI host | **DEFERRED**; do not mark the release passed on local evidence alone |

If the native engine cannot provide a zero-exposure boot interval, record the exact interval and
mechanism. The acceptable fallback is an interface that stays down until the gate passes. Do not claim
atomicity.

The runtime policy-routing rules are **not** made persistent by `edgeos-vxlan`. After every reboot they
must be restored separately (or by the maintainer's chosen mechanism). If Route64 connectivity is
missing after boot, reapply the routing rules first before attributing the failure to the VXLAN or
firewall code.

## 8. Upgrade, downgrade, and package removal (X, lab unit preferred)

Do not remove the integration while a production VXLAN interface is live; `prerm` refuses, and the
removal is destructive to the configuration.

| Step | Action | Pass criterion |
|---|---|---|
| 8.1 | Upgrade RC1 -> a second RC or final (lab unit preferred) | no interface recreation; attachments preserved; diversion hashes correct |
| 8.2 | Remove the VXLAN configuration and save | interfaces deleted; jumps removed by the reconciler |
| 8.3 | `sudo dpkg -r edgeos-vxlan` | refused while saved VXLAN config or live VXLAN interfaces exist; succeeds after both are gone |
| 8.4 | Verify `Vyatta::Interface.pm` restored | hash matches the original |
| 8.5 | Remove `edgeos-vxlan-kmod` | refused while live VXLAN interfaces exist; stock `udp_tunnel.ko` restored |
| 8.6 | Reinstall 0.2.2 and restore the baseline config | regression configuration works |

If removal is refused because `ip link show type vxlan` cannot determine the state, the package now
refuses rather than guessing; resolve the check manually before retrying.

## 9. Recovery and rollback (must remain usable if VXLAN/firewall reconciliation fails)

The management path is independent of `vxlan41913`; recovery is always possible through the
management address or console.

### 9.1 A commit fails and the interface is down

1. `show configuration commands | grep -A10 vxlan41913`
2. `ip -j -d link show dev vxlan41913` (JSON; the human `-d` output is broken)
3. `sudo iptables -S VYATTA_FW_IN_HOOK VYATTA_FW_OUT_HOOK VYATTA_FW_LOCAL_HOOK`
4. `sudo ip6tables -S VYATTA_FW_IN_HOOK VYATTA_FW_OUT_HOOK VYATTA_FW_LOCAL_HOOK`
5. `tail -50 /var/log/vyatta/vyatta-commit.log`

Do **not** manually force the interface up while it is down because a required attachment is not
effective. Either restore the previous attachment/ruleset and re-commit, or detach the attachment and
accept an unfiltered interface **only** if that is the explicit desired state. Detaching the
attachment is the supported way to return to an unfiltered interface:

```text
delete interfaces vxlan vxlan41913 firewall
commit
```

### 9.2 The native policy is wrong after migration

1. Detach the native `in`/`local` attachments.
2. Reapply the saved manual rules for `vxlan41913` from the backup (use `iptables-restore --noflush`
   with a filtered restore file, or the exact `-I`/`-A` commands; do not restore the full table over
   the live firewall).
3. Verify the management path and the manual counters.
4. Re-commit the native attachments only after the rulesets are corrected.

### 9.3 The commit engine is wedged or the router is unreachable

* Use the console.
* If the change was made with `commit-confirm`, wait for the automatic rollback or issue the rollback
  command for the previous revision.
* If the saved configuration is bad, restore the off-router `/config/config.boot` copy using the
  console and the platform's supported load/restore procedure, then reboot. Do not copy a backup over
  `/config/config.boot` while the system is running and expect a live recovery.
* Reboot only with console access and after capturing the runtime routing rules.

### 9.4 VXLAN connectivity fails but the router is reachable

1. Check the underlay peer filtering (`iptables -S`/`ip6tables -S` on the physical interface).
2. Check the native overlay chain counters.
3. Check FDB/NDP (`bridge fdb show dev vxlan41913`, `ip -6 neigh show dev vxlan41913`).
4. Check the runtime policy-routing rules/table after any reboot.
5. Roll back the last configuration change if the failure started with it.

## 10. Regression and final evidence

* Existing IPv4/IPv6 VXLAN interfaces without attachments: creation, identity change, recreation,
  bridge membership, rollback, save/reboot.
* Bridge and MTU hardware tests remain valid; the firewall subtree must not affect them.
* `ip -j -d link show` remains the diagnostic; `ip -d` human output is known-broken.

Return for each phase: command transcripts, `iptables-save`/`ip6tables-save` before/after, manual-rule
diff, `show configuration commands`, ifindex/interface state, native chain counters, probe logs with
timestamps, packet captures, runtime routing captures, and exact package versions. Mark each step
PASS / FAIL / NOT RUN / DEFERRED. A passing configuration without dataplane evidence is not a pass.
