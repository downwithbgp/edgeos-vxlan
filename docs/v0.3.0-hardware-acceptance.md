# v0.3.0 hardware acceptance procedure

**Status:** procedure prepared; **not executed**. No hardware was changed, rebooted, upgraded or
installed by the implementation work.

**Purpose:** establish that native firewall attachments on a routed VXLAN interface enforce the
intended policy in the dataplane across the supported lifecycle, and that no operational-but-unfiltered
interval can be observed.

**Supported platform:** Ubiquiti EdgeRouter X / ER-e50, EdgeOS 3.0.1 build 5862409, Linux
4.14.54-UBNT, MIPS little-endian.

**Evidence classes:** PASS requires dataplane evidence (probe logs, counters, captures), not merely a
configuration that looks correct. Steps are marked with a **disruption** class:

* **N — non-disruptive:** no production interface, policy or traffic change.
* **D — disruptive:** touches the production tunnel or its traffic; maintenance window required.
* **X — destructive:** deletes/recreates an interface or package; isolated or lab unit preferred.
* **R — reboot:** cold boot; requires console access and runtime-state restoration.

Every step also carries a **blast radius**:

* **L — local:** affects only the test interface's own traffic and dispatch; safe on the production
  unit when the test interface carries no production traffic.
* **R — router-wide:** affects other interfaces, traffic or hooks on the same router.
* **G — global:** replaces a system executable or changes system-wide state; **never on the
  production ER-X** — use a disposable router.
* **X — disposable only:** destructive to the device or package set.

**External-host dependency:** the OCI test host is currently unavailable. Independent Internet-facing
positive/negative tests are marked **DEFERRED — external host required**. Local-underlay and
router-originated tests can proceed; they are not equivalent.

### Evidence classes and VTEP roles

The local test VTEP (the `vxlan903` peer) and the remote Route64 VTEP are different systems on
different paths. A result from one is not evidence for the other. Record each class separately;
do not merge them into a single "connectivity works" claim.

| Class | What it proves | What it does not prove | Where |
|---|---|---|---|
| **Native-only structural verification** | The dispatch is exactly one jump per direction/family, the hooks are reachable from `INPUT`/`FORWARD`, the target chains end in the vendor default-action rule for the configured action, and no manual rule remains | That a packet traverses the native path; operator policy correctness | §6.4 (interface down), `iptables-save`/`ip6tables-save`, `--status` |
| **Router-originated application connectivity** | The router's own stack and routing can reach the Route64 application endpoint (source address, policy routing, local output path) | The forwarded dataplane through `vxlan41913`; the external Internet path; the `in`/`out` hooks | Router-originated `ping`/TLS/HTTP2 client to Route64; §6.5 |
| **Isolated dataplane verification** | The forwarding dataplane and the native `in`/`out`/`local` hooks enforce policy for the isolated `vxlan903` test VTEP with controlled hosts B and C | Route64 reachability, the remote VTEP, the production underlay path | Phase 3/4 with the local test peer |
| **Independent external positive/negative probes** | The Internet path and the remote Route64 VTEP/application are reachable/denied as expected, independent of the router's own origin | The local test VTEP's dataplane; the exact local hook path | External OCI host; positive and negative probes; §6.5/§7.6 |

* The local VTEP is a **test fixture**. It does not stand in for the remote Route64 VTEP, and a
  local VTEP probe does not prove Route64 connectivity.
* A router-originated ping to a Route64 address exercises the router's own output/routing path; it
  does not exercise `FORWARD -i vxlan41913` and cannot prove the `in` or `out` policy.
* The external probe is independent of the router's origin, but it proves the Internet path and the
  remote endpoint, not the local test dataplane or the exact local hook path.
* Each class gets its own PASS/FAIL. A missing class is NOT RUN or DEFERRED, not inferred from
  another class.

## 0. Safety, access, and preconditions

* Use a **disposable test router** for the destructive phases where possible. The production ER-X may
  be used for the isolated-interface phases only if a new VXLAN interface and its policy do not affect
  production traffic.
* **Never run a global intervention on the production ER-X:** replacing `/usr/sbin/ubnt-fw` or
  `/sbin/iptables`, inserting an unconditional rule into a shared `VYATTA_FW_*` hook, or removing
  packages. Use a disposable router for those; the scoped equivalents in Phase 5 are helper-level
  invocations with environment overrides.
* Do not run production-migration, reboot, package-removal or failure-injection steps without the
  maintainer's explicit approval and a maintenance window.
* **Management path must not depend on `vxlan41913`.** Use a physical/VLAN management address or the
  console. Test the path before starting.
* Have a **console** (serial or local) available for the production migration and reboot. Do not rely
  on SSH over the tunnel.
* Have a **local VTEP peer** for the isolated tests: a Linux host on the underlay with the VXLAN
  module, or a second disposable router. The OCI host is not required for this; a local host is
  sufficient for the dataplane semantics.
* Take a full configuration backup, a copy of `/config/config.boot`, and an off-router copy of
  `iptables-save`/`ip6tables-save`, `ip -6 rule`, `ip -6 route`, `ip -6 addr show dev lo`, and the
  interface-specific sysctl capture before any change (see §1).
* Record the package versions, the diverted `Vyatta::Interface.pm` hash, and the kernel module hashes.
* Use documentation address ranges in any evidence published outside the maintainer's environment.

## 1. Production-specific inventory (N)

The operational Route64 interface is `vxlan41913`. It currently has:

* manually installed IPv6 INPUT/FORWARD jumps to `HEv6_LOCAL` and `HEv6_IN`;
* interface-scoped IPv4 INPUT/FORWARD DROP rules;
* runtime-only IPv6 policy-routing rules and a dedicated routing table for the Route64 allocation;
* a runtime-only delegated-prefix test loopback address;
* interface-specific sysctls on the underlay, the VXLAN interface and `lo`.

`edgeos-vxlan` owns none of the runtime-only state below. A reboot removes it; capture it here and
restore it in Phase 7 before any connectivity claim.

### 1.1 Manual firewall rules

The manual rules can **mask** a failure of native enforcement. Capture them and their positions
exactly:

```bash
sudo iptables-save -t filter > /config/vxlan41913-pre.v4
sudo ip6tables-save -t filter > /config/vxlan41913-pre.v6
sudo iptables-save -t filter | grep -E 'vxlan41913|HEv6'
sudo ip6tables-save -t filter | grep -E 'vxlan41913|HEv6'
for chain in INPUT FORWARD; do sudo iptables -S "$chain"; done
for chain in INPUT FORWARD; do sudo ip6tables -S "$chain"; done
for chain in VYATTA_FW_IN_HOOK VYATTA_FW_OUT_HOOK VYATTA_FW_LOCAL_HOOK; do
    sudo iptables -S "$chain"
done
for chain in VYATTA_FW_IN_HOOK VYATTA_FW_OUT_HOOK VYATTA_FW_LOCAL_HOOK; do
    sudo ip6tables -S "$chain"
done
```

On the supported iptables version, `-S` accepts at most one chain argument. The loops above (or
`iptables-save -t filter`) are the valid form; do not pass multiple chains to one `-S` invocation.

Record the **rule order** of `INPUT` and `FORWARD`, not just the rule text. The native dispatch is
installed inside the `VYATTA_FW_*` hooks; if a manual rule sits before the hook that jumps to those
chains, it can shadow the native policy. If the manual rules are after the hook, they are redundant
but still mask counters.

### 1.2 Runtime IPv6 policy routing and table

Capture the runtime policy routing separately; it is **not** owned by `edgeos-vxlan`:

```bash
ip -6 rule show > /config/route64-rules-pre.txt
ip -6 route show table all > /config/route64-routes-pre.txt
ip -6 route show table <ROUTE64_TABLE> > /config/route64-table-pre.txt
```

Record the table number and the exact `ip -6 rule add ...` and `ip -6 route add ... table <N>`
commands needed to restore them. These rules are runtime-only and a reboot will remove them.

### 1.3 Delegated-prefix test loopback address

The deployment uses an address from the delegated prefix on `lo` as a local test endpoint. It is
not in `config.boot` and is lost on reboot. Capture it and record the exact restore command:

```bash
ip -6 addr show dev lo > /config/lo-addr-pre.txt
ip -6 route show table local | grep ' dev lo' >> /config/lo-addr-pre.txt
```

Record the address and prefix length, for example `<PREFIX>::<host>/128`. Restore it with:

```bash
sudo ip -6 addr add <PREFIX>::<host>/128 dev lo
```

If the address is already persistent on this router, record that fact and skip the restore; do not
add a duplicate.

### 1.4 Interface-specific sysctls

Capture the forwarding and per-interface sysctls that the deployment relies on. Include the global
forwarding switches, the underlay interface, `vxlan41913` (when present), `lo`, `all` and `default`:

```bash
sysctl -a 2>/dev/null |
    grep -E '^net\.(ipv4|ipv6)\.(ip_forward|conf\.)' > /config/sysctl-pre.txt
```

Review the capture and record which values differ from the platform defaults. Typical keys are
`net.ipv4.ip_forward`, `net.ipv6.conf.all.forwarding`, `net.ipv4.conf.<if>.rp_filter`,
`net.ipv6.conf.<if>.accept_ra`, `net.ipv6.conf.<if>.disable_ipv6`,
`net.ipv4.conf.<if>.proxy_arp` and `net.ipv6.conf.<if>.forwarding`, but use the captured values,
not this list as a default.

Restore non-default values with `sysctl -w` after the interface exists: the reconciler creates
`vxlan41913`, so its per-interface sysctls cannot be set before it appears. `sysctl -w` is
runtime-only; whether these values should be made persistent is a separate maintainer decision and
is not assumed by this procedure.

## 3. Isolated native attachment and dataplane (N for production; D for the test peer)

Use a disposable routed interface `vxlan903` with a local VTEP peer **and a routed client host C on
the router's LAN side**. This is the **isolated dataplane** class in §0; it is not evidence for the
remote Route64 VTEP. `in` and `out` are `FORWARD` hooks: they only see **forwarded** traffic.
Router-destined traffic exercises `local` (`INPUT`). Attaching only `in` and then pinging the
router's own address exercises the wrong hook.

```text
configure

set interfaces vxlan vxlan903 vni 903
set interfaces vxlan vxlan903 local-ip <underlay-local>
set interfaces vxlan vxlan903 remote-ip <local-peer>
set interfaces vxlan vxlan903 port 4789
set interfaces vxlan vxlan903 mtu 1450
set interfaces vxlan vxlan903 address 198.51.100.1/24
set interfaces vxlan vxlan903 address 2001:db8:903::1/64

set firewall name VXLAN903_IN default-action drop
set firewall name VXLAN903_IN rule 10 action accept
set firewall name VXLAN903_IN rule 10 protocol icmp
set firewall name VXLAN903_IN rule 20 action accept
set firewall name VXLAN903_IN rule 20 state established enable
set firewall name VXLAN903_IN rule 20 state related enable

set firewall name VXLAN903_LOCAL_IN default-action drop
set firewall name VXLAN903_LOCAL_IN rule 10 action accept
set firewall name VXLAN903_LOCAL_IN rule 10 protocol icmp
set firewall name VXLAN903_LOCAL_IN rule 20 action accept
set firewall name VXLAN903_LOCAL_IN rule 20 state established enable
set firewall name VXLAN903_LOCAL_IN rule 20 state related enable

set firewall ipv6-name VXLAN903_IN6 default-action drop
set firewall ipv6-name VXLAN903_IN6 rule 10 action accept
set firewall ipv6-name VXLAN903_IN6 rule 10 protocol icmpv6
set firewall ipv6-name VXLAN903_IN6 rule 20 action accept
set firewall ipv6-name VXLAN903_IN6 rule 20 state established enable
set firewall ipv6-name VXLAN903_IN6 rule 20 state related enable

set firewall ipv6-name VXLAN903_LOCAL_IN6 default-action drop
set firewall ipv6-name VXLAN903_LOCAL_IN6 rule 10 action accept
set firewall ipv6-name VXLAN903_LOCAL_IN6 rule 10 protocol icmpv6
set firewall ipv6-name VXLAN903_LOCAL_IN6 rule 20 action accept
set firewall ipv6-name VXLAN903_LOCAL_IN6 rule 20 state established enable
set firewall ipv6-name VXLAN903_LOCAL_IN6 rule 20 state related enable

set interfaces vxlan vxlan903 firewall in name VXLAN903_IN
set interfaces vxlan vxlan903 firewall in ipv6-name VXLAN903_IN6
set interfaces vxlan vxlan903 firewall local name VXLAN903_LOCAL_IN
set interfaces vxlan vxlan903 firewall local ipv6-name VXLAN903_LOCAL_IN6
set interfaces vxlan vxlan903 firewall out name VXLAN903_OUT

commit
```

Traffic matrix:

| Direction | Hook | Required traffic | Positive control | Negative control |
|---|---|---|---|---|
| `in` | `FORWARD -i vxlan903` | B → A → C (forwarded ingress) | a permitted protocol/port reaches a **verified listener** on C | a denied protocol/port does not reach the same listener |
| `out` | `FORWARD -o vxlan903` | C → A → B (forwarded egress) | permitted reaches a verified listener on B | denied does not reach it |
| `local` | `INPUT -i vxlan903` | B → A's own overlay address (router-destined) | permitted reaches the router | denied does not |

Before asserting a negative result, start a real listener on the destination and prove the positive
control through the same path, so "connection refused" (no listener) cannot be mistaken for a
policy drop.

| Step | Blast radius | Test | Pass criterion |
|---|---|---|---|
| 3.1 | L | `show configuration commands \| grep vxlan903` | attachments present |
| 3.2 | L | `show firewall name ...`; `show firewall ipv6-name ...` | rulesets present |
| 3.3 | L | `sudo iptables -S VYATTA_FW_IN_HOOK` | exactly one `-i vxlan903 -j VXLAN903_IN` jump |
| 3.4 | L | `sudo ip6tables -S VYATTA_FW_IN_HOOK` | exactly one `-i vxlan903 -j VXLAN903_IN6` jump |
| 3.5 | L | `for chain in INPUT FORWARD; do sudo iptables -S "$chain"; done` (same for `ip6tables`) | the hook jumps are present, reachable and not shadowed |
| 3.6 | L | forwarded IPv4 `in`: permitted then denied from B to the listener on C | permitted reaches C and increments the native chain; denied does not and increments the drop counter |
| 3.7 | L | forwarded IPv4 `out`: permitted then denied from C to the listener on B | as above in the egress direction |
| 3.8 | L | router-destined IPv4 `local`: permitted then denied from B to A | permitted reaches A; denied does not; counters |
| 3.9 | L | IPv6 NDP + ICMPv6 under `local` | neighbour resolution works; echo permitted/denied per policy |
| 3.10 | L | forwarded IPv6 `in`/`out` | permitted/denied per policy; counters |
| 3.11 | L | outer underlay UDP/4789 | untouched by the overlay attachment |
| 3.12 | L | unrelated interface policy | unchanged |
| 3.13 | L | `--status` in a configuration session | configured and effective pairs match |

Repeat the positive/negative pairs for `local` and `out`; never use router-originated traffic to
test `in`/`out` and never use forwarded traffic to test `local`.

### Effective-state negative checks (unit-verified; scoped on hardware)

These manipulate only the isolated interface's own dispatch/traffic. Do **not** run them on
`vxlan41913`.

1. **Duplicate jump (L).** `sudo iptables -A VYATTA_FW_IN_HOOK -i vxlan903 -j VXLAN903_IN`; run a
   commit that touches `vxlan903` (for example a description change) in a non-production window.
   Capture now fails as ambiguous; the commit must fail and the interface must be taken down. Remove
   the duplicate and re-commit.
2. **Interface-scoped shadow (L).** `sudo iptables -I VYATTA_FW_IN_HOOK 1 -i vxlan903 -j DROP`; run a
   commit. The gate must report a stale/shadowing same-interface rule and take the interface down.
3. **Emptied target chain (L).** Empty `VXLAN903_IN`; the gate must report an empty chain and take the
   interface down.
4. **Source-scoped shadow (L).** `sudo iptables -I VYATTA_FW_IN_HOOK 1 -s <test-peer>/32 -j DROP`; the
   gate must report the hook as shadowed and take the interface down. This affects only the test
   peer's traffic and is the scoped replacement for a global DROP.
5. **Global drop in a shared hook (R — disposable router only).** A global `-j DROP` in
   `VYATTA_FW_IN_HOOK` affects every interface dispatched through that hook. Do not run it on the
   production ER-X; use a disposable router if the unconditional-shadow branch must be exercised.

These tests prove the gate on the real `iptables -S` output. Do not run the global variant on
`vxlan41913`.

## 4. Destructive lifecycle on the isolated interface (X, isolated only)

Run a continuous negative probe (timestamped, ≤100 ms interval) **and** a positive control during
every step of this phase, not only during recreation. Record probe start/stop times.

| Step | Blast radius | Action | Pass criterion |
|---|---|---|---|
| 4.1 | L | Replace `VXLAN903_IN` with `VXLAN903_IN_B` under a continuous probe | commit succeeds; jump replaced atomically; no netdevice recreation (ifindex unchanged); **no successful denied probe**; counters move for the new chain |
| 4.2 | L | Delete the attachment | jump removed; interface still up; unrelated rules unchanged |
| 4.3 | L | Add a second isolated VXLAN sharing the ruleset | both jumps present; deleting one leaves the other |
| 4.4 | R/L | Change a rule inside the attached ruleset under a continuous probe | the vendor rebuilds the chain; **no successful denied probe**; record the observed transition |
| 4.5 | L | `disable` then enable vxlan903 | down with jump present; up with jump present; gate passes |
| 4.6 | L | Delete the attached ruleset while attached | commit fails with a "still in use" error; jump remains |
| 4.7 | L | Rename a ruleset and update the attachment in one commit | commit succeeds with the new chain, or fails without leaving the interface unprotected; record exact behaviour |
| 4.8 | L | `commit-confirm` with a policy change and no confirm | rollback restores the previous policy and interface state |
| 4.9 | L | Change VNI, UDP port, remote-IP in turn under a continuous probe | interface recreated; jump survives (name-based); no successful denied probe |
| 4.10 | L | Change VNI and attachment in one commit under a continuous probe | new jump installed; no successful denied probe |
| 4.11 | L | Failure injection (Phase 5) | old state restored or interface down; explicit error |

The continuous probe must run across **live attachment replacement (4.1) and independent ruleset
modification (4.4)**, not only recreation (4.9–4.11). The ifindex must change while the jump remains.

## 5. Failure injection (X, isolated interface only)

All injections must be reversible and performed on the isolated `vxlan903` with approval. Record the
exact commands. Each injection is classified by blast radius:

* **L** — scoped to the isolated interface/helper invocation; safe on the production unit when the
  test interface carries no production traffic.
* **G** — a system-wide change (replacing `/usr/sbin/ubnt-fw` or `/sbin/iptables`). **Never on the
  production ER-X.** Use a disposable router, or the equivalent helper-level invocation with the
  environment overrides on the isolated interface (which tests the helper, not the commit engine).

| # | Blast radius | Injection | Expected |
|---|---|---|---|
| 5.1 | L | Set an attachment to a nonexistent ruleset | commit fails at validation before mutation; the old jump and interface are unchanged |
| 5.2 | L | Run the helper directly as `vyattacfg` with `vxlan_bin_ubnt_fw=/tmp/fail-fw` (a wrapper that exits 1 for `update-interface` and delegates the rest) on an isolated interface | helper restores the old state; a new attachment leaves the interface down; the error names the interface and attachment |
| 5.3 | G | Replace the system `ubnt-fw` with the same wrapper and commit through the engine (disposable router only) | commit fails; no operational-unfiltered interface |
| 5.4 | L | Run the helper directly with `vxlan_bin_iptables=/tmp/wrap-iptables` whose `-S` output omits the dispatch (or returns a stale same-interface rule) | the gate reports `missing`/`malformed or stale`; the interface is down |
| 5.5 | G | Replace the system `iptables`/`ip6tables` with that wrapper (disposable router only) | commit fails; interface down |
| 5.6 | L | Recreate with a post-apply failure using the helper-level `ubnt-fw` wrapper (the commit-engine variant is G, disposable router) | the interface rolls back to the old identity and old jump; if restoration fails, the interface is down |
| 5.7 | L | Duplicate the interface jump before a commit | capture fails as ambiguous; commit fails; interface down |
| 5.8 | L | Insert a source-scoped shadow before the dispatch (`-I ... -s <peer>/32 -j DROP`) | the gate reports "shadowed"; commit fails; interface down |
| 5.9 | L | Empty the target chain | the gate reports "empty"; commit fails; interface down |

The verification-failure injection must target the path the implementation actually uses: the gate
parses `iptables -S`, so make `-S` return a missing/stale table rather than making `iptables -C`
fail. `-C` is only the immediate post-update presence check.

After each injection: restore the original files/environment, re-commit, and verify convergence. Do
not leave a wrapper in place.

## 6. Production migration of `vxlan41913` (D)

**Precondition:** Phases 3–5 pass on the isolated interface, and the maintainer has approved the
maintenance window. Console access is available. The full `iptables-save`/`ip6tables-save` backups,
the exact manual-rule list and the `ip -6 rule`/route captures are off-router. The management path
does not depend on `vxlan41913`.

**Why the handover is quiesced.** The production interface is protected by manual rules that precede
the `VYATTA_FW_*` hooks in `INPUT`/`FORWARD`: interface-scoped IPv4 `DROP` rules and IPv6 jumps to
`HEv6_LOCAL`/`HEv6_IN`. While those rules remain, the native hooks are shadowed for this interface,
so **native counters cannot increase and a counter-based proof of native enforcement is
impossible**. The migration therefore quiesces the interface, changes protection while it is down,
and proves the native path only after the manual rules are gone. At every step either the interface
is down, or the only effective policy is the intended one.

### 6.1 Prepare the native policy (no traffic change)

Translate the intended manual policy into native rulesets. Do not blindly copy the manual chain
contents; review the intent:

* `HEv6_LOCAL_NATIVE` — router-destined IPv6: NDP/ICMPv6 essentials, established/related, explicit
  management, intended default action.
* `HEv6_IN_NATIVE` — forwarded IPv6: intended allow/deny, established/related, default action.
* `VXLAN41913_IN4` — inner IPv4: `default-action drop`, matching the interface-scoped IPv4
  `INPUT`/`FORWARD` drop.

The intended policy covers **both address families and both ingress directions** (`in` and `local`).
There is no native `out` policy because the production intent filters only ingress.

```text
set firewall name VXLAN41913_IN4 default-action drop
set firewall ipv6-name HEv6_IN_NATIVE ...
set firewall ipv6-name HEv6_LOCAL_NATIVE ...
commit
```

Verify each chain is built, non-empty and ends in the vendor default-action rule for the configured
action:

```bash
sudo iptables -S VXLAN41913_IN4
sudo ip6tables -S HEv6_IN_NATIVE
sudo ip6tables -S HEv6_LOCAL_NATIVE
```

Do not attach anything yet.

### 6.2 Quiesce the interface

```text
set interfaces vxlan vxlan41913 disable
commit
```

The reconciler takes the interface down. Confirm with `ip -j link show dev vxlan41913`
(`operstate`/`flags`) and with a probe that no traffic passes. The manual rules are still present;
while the interface is down nothing can bypass them because no packet traverses the interface. Any
later commit on this interface keeps it down while `disable` is set.

Re-check the management path and the console.

### 6.3 Remove the manual rules while down

Using the exact commands from the Phase 1 backup, remove:

* the interface-scoped IPv4 `INPUT` and `FORWARD` `DROP` rules;
* the manual IPv6 `INPUT` and `FORWARD` jumps to `HEv6_LOCAL`/`HEv6_IN`.

Because the interface is administratively down, removing the manual protection creates **no
exposure**. Do not remove them one at a time while the interface is up: that requires proving native
enforcement through a path the remaining manual rules shadow.

Verify that no manual `vxlan41913`/`HEv6` rules remain:

```bash
sudo iptables-save -t filter | grep -E 'vxlan41913|HEv6' || true
sudo ip6tables-save -t filter | grep -E 'vxlan41913|HEv6' || true
```

### 6.4 Attach the complete native policy while down

```text
set interfaces vxlan vxlan41913 firewall in name VXLAN41913_IN4
set interfaces vxlan vxlan41913 firewall local name VXLAN41913_IN4
set interfaces vxlan vxlan41913 firewall in ipv6-name HEv6_IN_NATIVE
set interfaces vxlan vxlan41913 firewall local ipv6-name HEv6_LOCAL_NATIVE
commit
```

The reconciler applies the dispatches, runs its gate (exact dispatch, hook reachability, terminal
default) and leaves the interface down because `disable` is set. If the commit fails, go to §6.6.

**Structural verification** (interface still down — this is the structural proof, not a dataplane
proof):

1. Exactly one exact jump per direction/family in its hook:
   ```bash
   for chain in VYATTA_FW_IN_HOOK VYATTA_FW_LOCAL_HOOK; do
       sudo iptables -S "$chain"
   done
   for chain in VYATTA_FW_IN_HOOK VYATTA_FW_LOCAL_HOOK; do
       sudo ip6tables -S "$chain"
   done
   ```
2. The hooks are reachable from the base chains and no rule shadows this interface:
   ```bash
   for chain in INPUT FORWARD; do sudo iptables -S "$chain"; done
   for chain in INPUT FORWARD; do sudo ip6tables -S "$chain"; done
   ```
3. The target chains are non-empty and end in the vendor default-action rule matching the configured
   action (step 6.1).
4. No manual `vxlan41913`/`HEv6` rule remains.

Do not activate the interface until all four pass.

### 6.5 Activate and prove the native-only dataplane

```text
delete interfaces vxlan vxlan41913 disable
commit
```

The reconciler re-runs the gate and brings the interface up; native enforcement is now the only
path. Zero the native chain counters, then record the three non-structural evidence classes
separately (see §0):

1. **Router-originated application connectivity.** From the router itself, reach the Route64
   application endpoint (the same client/protocol the deployment uses, for example `ping`, TLS or
   HTTP/2). This exercises the router's own source address, policy routing and output path; it does
   **not** exercise `FORWARD -i vxlan41913` and is not evidence for the forwarded `in`/`out` policy.
2. **Isolated dataplane on the local test VTEP.** With the local underlay peer and the routed client,
   run the permitted/denied matrix for `in`, `out` and `local`:
   * permitted traffic passes and increments the native chain counters;
   * denied traffic is dropped and increments the native chain counters;
   * the management path is unaffected.

   This proves the local dataplane and the native hooks for the local peer. It does **not** prove the
   remote Route64 VTEP or the Internet path.
3. **Independent external positive/negative probes.** From the external OCI host, probe the Route64
   transfer address and an address from the routed /56. These prove the Internet path and the remote
   endpoint, independently of the router's origin, but not the local test dataplane. **DEFERRED**
   until the external host is available; do not substitute the local VTEP result.

Because the manual rules are gone, the counters now prove the native path for the local dataplane.
If any check fails, go to §6.6 immediately.

### 6.6 Rollback (fail-closed, usable at any stage)

1. **Quiesce first.** If the interface is up, `set interfaces vxlan vxlan41913 disable` + `commit`
   (or `ip link set dev vxlan41913 down` if the commit path itself is broken). Confirm it is down.
2. **Restore the manual protection while down** with a filtered `iptables-restore --noflush` of the
   saved manual rules (or the exact `-I` commands at their original positions). Never restore the
   full table over the live firewall.
3. **Verify the manual protection structurally**: the rules are present and precede the
   `VYATTA_FW_*` hooks.
4. **Only then** remove the native enforcement while still down:
   ```text
   delete interfaces vxlan vxlan41913 firewall
   commit
   ```
5. **Only then** reactivate:
   ```text
   delete interfaces vxlan vxlan41913 disable
   commit
   ```
6. Verify the manual counters and probes, and the management path.

The order matters: protection is restored **before** native enforcement is removed and **before**
the interface is reactivated. Keep the backups.

When the migration completes, confirm the only `vxlan41913` dispatch is the native
`VYATTA_FW_*` jump.

## 7. Cold boot and fail-open detection (R, D)

The external OCI probe host is unavailable. The **Internet-facing** continuous negative probe is
**DEFERRED — external host required**. A local probe on the underlay/overlay can still be run and is
required; it does not cover the Internet path.

The evidence classes in §0 apply throughout this phase. The **local VTEP** probe and an **external
Route64** probe are different classes: the local probe proves the local dataplane, not the Internet
path to the remote VTEP; the external probe proves the Internet path and the remote endpoint, not the
local dataplane. Both are required and neither replaces the other; record them separately.

Before the reboot:

1. Save the configuration.
2. Capture the complete runtime-only state: policy-routing rules and table (`ip -6 rule`,
   `ip -6 route show table <N>`), the delegated-prefix test loopback address
   (`ip -6 addr show dev lo`), the interface-specific sysctls (`/config/sysctl-pre.txt`), and the
   manual-rule restore commands from Phase 1.
3. Write down the restore order: policy routing, loopback address, then per-interface sysctls after
   the VXLAN interface exists, then probes.
4. Start the local probe that must be denied (for example IPv6 TCP/8080 to an overlay address), at
   100 ms, logging timestamps.
5. Have the console ready.

| Step | Action | Pass criterion |
|---|---|---|
| 7.1 | Cold boot | no successful denied probe; after boot the interface is up and the native jump is present |
| 7.2 | Reapply the runtime Route64 policy-routing rules/table immediately | `ip -6 rule` and `ip -6 route show table <N>` match the pre-boot capture |
| 7.2a | Reapply the delegated-prefix test loopback address | `ip -6 addr show dev lo` matches the pre-boot capture; no duplicate |
| 7.2b | Reapply the interface-specific sysctls after `vxlan41913` exists | each captured non-default `sysctl -n` value matches |
| 7.3 | Inspect the boot/commit logs | no firewall attachment error; if there is one, the interface is down |
| 7.4 | `show configuration commands`, `show interfaces`, `ip -j -d link show`, native chain counters | configuration and effective state agree |
| 7.5 | Repeat the boot with the local probe started before the router finishes booting | same; record any successful denied probe (must be none) |
| 7.6 | External probe from the OCI host | **DEFERRED**; do not mark the release passed on local evidence alone |

If the native engine cannot provide a zero-exposure boot interval, record the exact interval and
mechanism. The acceptable fallback is an interface that stays down until the gate passes. Do not claim
atomicity.

The runtime policy-routing rules, the delegated-prefix test loopback address and the
interface-specific sysctls are **not** made persistent by `edgeos-vxlan`. After every reboot they
must be restored separately (or by the maintainer's chosen mechanism), in the order above. If
Route64 connectivity is missing after boot, restore the runtime-only state first before attributing
the failure to the VXLAN or firewall code.

## 8. Upgrade, downgrade, and package removal (X, lab unit preferred)

Do not remove the integration while a production VXLAN interface is live; `prerm` refuses, and the
removal is destructive to the configuration.

| Step | Blast radius | Action | Pass criterion |
|---|---|---|---|
| 8.1 | X | Upgrade RC2 -> RC3 (lab unit preferred) | no interface recreation; attachments preserved; diversion hashes correct |
| 8.2 | X | Remove the VXLAN configuration and save | interfaces deleted; jumps removed by the reconciler |
| 8.3 | X | `sudo dpkg -r edgeos-vxlan` | refused while saved VXLAN config or live VXLAN interfaces exist; succeeds after both are gone |
| 8.4 | X | Verify `Vyatta::Interface.pm` restored | hash matches the original |
| 8.5 | X | Remove `edgeos-vxlan-kmod` | refused while live VXLAN interfaces exist; stock `udp_tunnel.ko` restored |

If removal is refused because `ip link show type vxlan` cannot determine the state, the package now
refuses rather than guessing; resolve the check manually before retrying.

## 9. Recovery and rollback (must remain usable if VXLAN/firewall reconciliation fails)

The management path is independent of `vxlan41913`; recovery is always possible through the
management address or console.

### 9.1 A commit fails and the interface is down

1. `show configuration commands | grep -A10 vxlan41913`
2. `ip -j -d link show dev vxlan41913` (JSON; the human `-d` output is broken)
3. `for chain in VYATTA_FW_IN_HOOK VYATTA_FW_OUT_HOOK VYATTA_FW_LOCAL_HOOK; do sudo iptables -S "$chain"; done`
4. `for chain in VYATTA_FW_IN_HOOK VYATTA_FW_OUT_HOOK VYATTA_FW_LOCAL_HOOK; do sudo ip6tables -S "$chain"; done`
5. `tail -50 /var/log/vyatta/vyatta-commit.log`

Do **not** manually force the interface up while it is down because a required attachment is not
effective. Either restore the previous attachment/ruleset and re-commit, or detach the attachment and
accept an unfiltered interface **only** if that is the explicit desired state. Detaching the
attachment is the supported way to return to an unfiltered interface:

```text
delete interfaces vxlan vxlan41913 firewall
commit
```

### 9.2 The native policy is wrong after migration

The rollback must restore protection **before** native enforcement is removed and **before** the
interface is reactivated.

1. Quiesce the interface (`set interfaces vxlan vxlan41913 disable` + `commit`, or
   `ip link set dev vxlan41913 down` if the commit path itself is broken). Confirm it is down.
2. Reapply the saved manual rules for `vxlan41913` from the backup (filtered
   `iptables-restore --noflush`, or the exact `-I` commands at their original positions; never a
   full-table restore over the live firewall).
3. Verify structurally that the manual rules are present and precede the `VYATTA_FW_*` hooks.
4. Detach the native `in`/`local` attachments **while still down**.
5. Reactivate the interface and verify the manual counters/probes and the management path.
6. Re-commit corrected native attachments only after the rulesets are fixed, following §6.

### 9.3 The commit engine is wedged or the router is unreachable

* Use the console.
* If the change was made with `commit-confirm`, wait for the automatic rollback or issue the rollback
  command for the previous revision.
* If the saved configuration is bad, restore the off-router `/config/config.boot` copy using the
  console and the platform's supported load/restore procedure, then reboot. Do not copy a backup over
  `/config/config.boot` while the system is running and expect a live recovery.
* Reboot only with console access and after capturing the runtime-only state (policy routing/table,
  delegated-prefix loopback address, interface-specific sysctls).

### 9.4 VXLAN connectivity fails but the router is reachable

1. Check the underlay peer filtering (`iptables -S`/`ip6tables -S` on the physical interface).
2. Check the native overlay chain counters.
3. Check FDB/NDP (`bridge fdb show dev vxlan41913`, `ip -6 neigh show dev vxlan41913`).
4. Check the runtime-only state after any reboot: policy-routing rules/table, the delegated-prefix
   loopback address and the interface-specific sysctls.
5. Roll back the last configuration change if the failure started with it.
