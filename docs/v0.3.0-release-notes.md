# edgeos-vxlan v0.3.0 — release notes

**Release:** `v0.3.0` — package version `0.3.0+edgeos3.0.1.e50`.
**Platform:** Ubiquiti EdgeRouter X / ER-e50, EdgeOS 3.0.1 build 5862409, Linux `4.14.54-UBNT`
(MIPS).

v0.3.0 adds native EdgeOS firewall attachments for VXLAN interfaces while keeping the v0.2.x
interface feature set. It is a release of the implementation qualified on hardware as RC5
(`0.3.0~rc5+edgeos3.0.1.e50`); the final packages contain the same runtime payload, with only
version, packaging and documentation changes.

## Highlights

* **Native EdgeOS firewall attachments** for `interfaces vxlan vxlanN`: the vendor firewall
  rulesets are attached through the existing `VYATTA_FW_*` hooks, and the interface is reconciled
  with its configuration.
* **IPv4 and IPv6 `in`, `out` and `local` support.** Each direction/family attaches a named
  ruleset; the firewall subtree is optional and existing unfiltered configurations keep their
  behaviour.
* **Fail-closed lifecycle management.** Attachments are captured, validated, applied and verified;
  a failure restores the previous dispatch where possible and leaves the interface down if the
  configured enforcement cannot be established.
* **Firewall-aware interface reconciliation and rollback.** Replacements and insertions stay
  nondisruptive; removals and compound changes are quiesced; a failed transaction restores the
  pre-change dispatch and administrative state or stops the interface.
* **Effective ruleset and dispatch verification.** Exactly one exact dispatch per direction/family,
  hook reachability, a non-empty chain, the vendor terminal default-action rule, the configured
  default action, and presence of every configured rule number (bounded vendor-comment check). An
  unreadable configuration or rule list is an API failure, not an empty policy.
* **Xtables lock contention handling.** Helper `iptables`/`ip6tables` calls wait on the lock;
  concurrent administration or monitoring no longer aborts an attachment transaction.
* **Compatibility with existing v0.2.2 configurations.** Configurations without firewall
  attachments upgrade without changes; the interface feature set is unchanged.

## Hardware qualification (EdgeRouter X)

RC5 was qualified on the ER-X, including:

* the six-combination isolated dataplane matrix (`in`/`out`/`local` × IPv4/IPv6) with counter
  evidence;
* the attachment lifecycle: replacement, removal, shared-ruleset modification, administrative
  disable/enable, VNI recreation, commit-confirm rollback and failed-transaction recovery;
* interrupted transactions (helper termination and controlling-session termination during the
  mutation window) — fail-closed, never an operational interface with partial enforcement;
* the **quiesced migration of the operational routed WAN interface `vxlan41913`** from manual
  netfilter rules to four native ingress attachments (`in`/`local` × IPv4/IPv6) with the intended
  policy preserved;
* **saved-configuration restoration after reboot**, including materialisation of the native
  firewall rulesets and dispatches, and restoration of the runtime-only Route64 state.

**Demonstrated third-party interoperability:** the migrated `vxlan41913` interface interoperates
with the Route64 VXLAN service (router-originated next-hop, transfer-address and delegated-prefix
connectivity, and source-specific routing through the dedicated table). Independent
Internet-facing probes remain deferred (see below).

## Supported configuration workflows

* Interactive EdgeOS CLI configuration for firewall ruleset creation and modification — supported.
* Scripted (script-template) VXLAN configuration referencing existing, correctly materialised
  rulesets — supported.
* Scripted firewall ruleset creation/modification — **not supported** on EdgeOS 3.0.1.
* Combined ruleset creation and attachment — interactive only.
* Boot-time restoration — verified on the qualified build.
* Commit-confirm and rollback — supported interactively.

See `docs/v0.3.0-support-boundary.md` for the full matrix.

## Important limitations

* **EdgeOS 3.0.1 scripted-commit firewall defect.** A scripted (script-template) commit can
  misapply `firewall name`/`ipv6-name` changes: a new ruleset can fail, and an existing ruleset can
  be silently reduced to its default action while the commit succeeds. **Use the interactive CLI
  for firewall ruleset changes.** The package does not patch the vendor and cannot make a scripted
  commit safe. This limitation is recorded in
  `docs/v0.3.0-edgeos-scripted-commit-limitation.md`.
* **Bridged firewall attachments are not supported.** A VXLAN interface configured as a bridge
  member refuses firewall attachments; bridged L2 traffic remains unfiltered by this extension.
* **Not a continuous firewall integrity monitor.** The extension manages enforcement during its
  own configuration lifecycle and verifies the effective state when it reconciles an interface. It
  does not continuously monitor vendor-managed rulesets and cannot protect against arbitrary
  out-of-band changes made outside its lifecycle.
* **No absolute atomicity/uninterrupted-enforcement guarantee.** Individual operations and the
  tested transitions are fail-closed, but the platform does not provide a general transactional
  guarantee across every possible interruption; the observed behaviour and the recovery procedure
  are documented in the qualification record.
* **Runtime-only Route64 state must be re-applied after reboot.** The IPv6 RPDB rules, dedicated
  table 41913 routes, loopback test address and interface sysctls are not part of the saved EdgeOS
  configuration; the hardware qualification used a separate restoration script. Persistent
  source-address-dependent routing remains a separate project and is **not** part of
  edgeos-vxlan.
* **Deferred tests.** Independent Internet-facing (OCI) positive/negative probes, unsolicited
  inbound tests, and forwarded dataplane tests from active delegated-prefix clients were not
  executed. Router-originated connectivity is not equivalent to these tests, and no claim of
  Internet-facing acceptance is made. The deferred probes are a limitation on Internet-facing
  acceptance claims, not a blocker for the generic VXLAN implementation.

## Upgrade and recovery

Existing v0.2.2 installations upgrade in place with both packages in one `dpkg` transaction,
kernel package first; the upgrade does not change existing VXLAN configuration or recreate
interfaces. The v0.3.0 packages were also installed over the qualified RC5 packages on the ER-X
and verified (same runtime payload). Previous release artifacts (v0.2.2 and the RC5 recovery pair)
remain available for recovery.
